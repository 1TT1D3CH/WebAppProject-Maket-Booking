-------------------------------------------------------------------------------
 สรุปภาพรวม (TL;DR)
-------------------------------------------------------------------------------
UI ทำมาค่อนข้างดี (canvas ลากวาง, หน่วยเมตร, dark mode, ระบบแจ้งเตือนแบบรวมข้อความ)
แต่ "ความปลอดภัยแทบไม่มีเลย": Firestore rules เปิดให้ทุกคนเขียน/ลบได้, ใครก็สลับเป็น
Owner/Admin ได้ด้วยปุ่มเดียว, เลขบัตรประชาชนและเบอร์โทรอ่านได้สาธารณะ และ repo มี
.env + node_modules + dist ถูก commit ขึ้น git

สิ่งที่ควรทำก่อน 5 อันดับแรก:
  1. เพิ่ม .gitignore แล้วเอา node_modules/, dist/, .env ออกจาก git    (ข้อ A1, A2)
  2. เขียน firestore.rules ใหม่ให้เช็คสิทธิ์ตาม role จริง                 (ข้อ B1-B4)
  3. ปิด Demo role switch / isAuthenticated=true ในเวอร์ชันใช้งานจริง และห้ามผู้ใช้เลือก role เอง (B5-B7)
  4. แก้บั๊กการแจ้งเตือน id ไม่ตรงกัน และปุ่ม "ลบทั้งหมด" ที่ลบแจ้งเตือนของทุกคน (C1, C2)
  5. แก้การ save ผังที่เขียนทับการจองของลูกค้า (C4, C5)

===============================================================================
 B. ความปลอดภัย / สิทธิ์การเข้าถึง / ข้อมูลส่วนบุคคล (PDPA)
===============================================================================

B1 [วิกฤต] firestore.rules เปิดเขียนสาธารณะ
   - markets:       allow write: if true          (ใครก็แก้/ลบผังตลาดได้)
   - stalls:        allow create, update, delete: if true
   - notifications: allow read, write: if true    (ใครก็อ่าน/ลบแจ้งเตือนของคนอื่นได้)
   - bookings:      allow read: if true           (ชื่อ+เบอร์โทรลูกค้าทุกคนอ่านได้สาธารณะ)
   แนะนำ: ตรวจ role จาก custom claims หรือจาก get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role
   และแยกสิทธิ์: อ่านผังได้ทุกคน, เขียนผังเฉพาะ admin/owner, notification อ่านได้เฉพาะ
   resource.data.tenantId == request.auth.uid

B2 [วิกฤต] ฟังก์ชัน isAdmin() ในกฎผิด
   firestore.rules บรรทัด 12:
     request.auth.token.role == 'admin' || request.auth.token.email != null
   -> ผู้ใช้ทุกคนที่สมัครด้วยอีเมลถือว่าเป็น admin ทั้งหมด

B3 [วิกฤต] collection users อ่านได้โดย "ทุกคนที่ล็อกอิน" รวมถึง anonymous
   - firebaseService.js initAuthListener() สั่ง signInAnonymously อัตโนมัติให้ทุกผู้เข้าชม
   - users เก็บ phone และ citizenId (เลขบัตรประชาชน)
   -> ผู้เข้าชมเว็บใครก็ได้สามารถดึงเลขบัตรประชาชนของผู้ใช้ทุกคนได้ = ผิด PDPA
   แนะนำ: allow read: if request.auth.uid == userId || isAdmin()
   และพิจารณาว่าจำเป็นต้องเก็บเลขบัตรประชาชนจริงหรือไม่

B4 [วิกฤต] ผู้ใช้เขียน document ของตัวเองได้ทั้งหมด รวมถึงฟิลด์ role
   - rules: allow write: if request.auth.uid == userId
   - AuthModal.vue บรรทัด 128-138 ให้ผู้สมัคร "เลือก role เองได้" รวมถึง owner/admin
   แนะนำ: สมัครได้แค่ tenant, ห้ามแก้ฟิลด์ role ใน rules
   (request.resource.data.role == resource.data.role) และให้ owner เป็นคนเลื่อนสิทธิ์

B5 [วิกฤต] authStore เริ่มต้นเป็น "ล็อกอินแล้ว" เสมอ
   - authStore.js บรรทัด 42-43: currentUser = DEMO_USERS.tenant, isAuthenticated: true
   - ดังนั้นเงื่อนไข "ต้องล็อกอินก่อนจอง" ใน BookingModal.vue บรรทัด 20 ไม่มีวันทำงาน
   - หลัง logout แล้ว refresh หน้า จะกลับมาเป็น demo tenant อีก

B6 [วิกฤต] ปุ่ม Quick Demo Role Switch (Owner/Admin/Tenant) แสดงให้ทุกคนใช้ได้
   - AuthModal.vue บรรทัด 33-66 -> ใครก็กดเป็น Owner ได้ทันทีโดยไม่ต้องใช้รหัสผ่าน
   - DEMO_USERS มีเลขบัตรประชาชน/เบอร์โทร (ข้อมูลสมมติ) ฝังในโค้ด
   แนะนำ: แสดงเฉพาะเมื่อ import.meta.env.DEV หรือมี flag VITE_DEMO_MODE

B7 [วิกฤต] ไม่มีการป้องกันโหมด Admin Builder
   - Navbar.vue บรรทัด 34-43: ปุ่ม "Admin Builder" แสดงให้ทุก role กด
   - marketStore.js บรรทัด 14: activeMode เริ่มต้นเป็น 'admin' -> ผู้เช่าเปิดเว็บมาเจอหน้าแก้ผังทันที
   - ผู้เช่ากด "บันทึกผัง" -> เขียนลง Firestore ได้ (เพราะ rules เปิด)
   แนะนำ: setMode('admin') ต้องเช็ค authStore.isAdmin, ค่าเริ่มต้นเป็น 'customer'

B8 [สูง] สถานะผู้ใช้เชื่อจาก localStorage ('auth_user') โดยตรง
   - แก้ค่าใน DevTools เป็น role: 'owner' ก็ได้สิทธิ์ทันที (ฝั่ง UI)
   - authStore ไม่ได้ subscribe onAuthStateChanged เลย ทำให้ state ฝั่ง UI กับ Firebase Auth
     ไม่ตรงกัน ส่วน marketStore มี currentUser ของตัวเองแยกอีกชุด (ซ้ำซ้อน)
   แนะนำ: ใช้ onAuthStateChanged เป็นแหล่งความจริงเดียว แล้วโหลด profile จาก users/{uid}

B9 [สูง] ข้อมูลผู้จอง (ชื่อ, เบอร์โทร, ประเภทสินค้า) ถูกฝังใน stalls[].bookedBy
   ภายใน document markets/main-layout ซึ่ง allow read: if true
   -> ลูกค้าทั่วไปเห็นเบอร์โทรของผู้เช่าทุกคน
   แนะนำ: เก็บข้อมูลส่วนตัวไว้ใน bookings/{id} ที่อ่านได้เฉพาะเจ้าของ+admin
   ในผังเก็บแค่ status และ bookingId

B10 [กลาง] หลัง logout, initAuthListener จะ signInAnonymously อัตโนมัติอีกรอบ
   (firebaseService.js บรรทัด 31-35) ทำให้ไม่มีสถานะ "ออกจากระบบ" จริง

B11 [กลาง] มี console.log ข้อมูลภายในจำนวนมากใน production

 C. บั๊ก / Logic ผิด
===============================================================================

C1 [สูง] notification: id ของ document ใน Firestore ไม่ตรงกับ id ที่ใช้ลบ/อ่าน
   - notificationStore.js บรรทัด 143 และ 175 สร้าง id เองแบบ 'notif-xxx' แล้ว addDoc()
     ซึ่ง Firestore สร้าง doc id แบบสุ่มอีกตัว
   - บรรทัด 98: remoteItems.push({ id, ...data }) -> data.id ('notif-xxx') ทับ doc id
   - markAsRead / deleteNotification เรียก doc(db,'notifications', id) ด้วย 'notif-xxx'
     ซึ่งไม่มีอยู่จริง -> update/delete ล้มเหลวแบบเงียบ (.catch(() => {}))
   ผลคือ: กดอ่านแล้ว/ลบแล้ว ไม่ถูกบันทึกบน Firestore จริง แค่ซ่อนไว้ใน localStorage
   แนะนำ: ใช้ setDoc(doc(db,'notifications', notifItem.id), ...) หรือไม่ใส่ฟิลด์ id
   แล้วใช้ { ...data, id: docSnap.id }

C2 [วิกฤต] การลบแจ้งเตือนส่งผลกับทุกคน
   - clearAllNotifications() (บรรทัด 236-257) ลบทุก document ใน collection notifications
     และปุ่ม "ล้างทั้งหมด" ใน NotificationCenter แสดงให้ tenant กดได้
     -> ผู้เช่าคนหนึ่งกด = แจ้งเตือนของผู้เช่าทุกคนหายหมด
   - autoCleanupIfSpammed() (บรรทัด 120-131) ถูกเรียกทุกครั้งที่เปิดแอป และถ้ามีเกิน 40
     รายการจะลบทิ้งทั้งหมดของทุกคน (ข้อมูลหาย, และเป็นการแก้ปัญหาที่ปลายเหตุ)
   แนะนำ: ลบเฉพาะของ user ตัวเอง, ถ้าต้องการ cleanup ให้ทำผ่าน Cloud Function / TTL policy

C3 [สูง] tenant fallback 'demo-tenant-001' ทำให้แจ้งเตือนรั่วข้ามผู้ใช้
   - notificationStore.js บรรทัด 53, 62, 214: filter รวม n.tenantId === 'demo-tenant-001'
     ด้วยเสมอ -> ผู้เช่าทุกคนเห็นแจ้งเตือนของ demo tenant
   - marketStore.js บรรทัด 537, 654, 701 และ firebaseService.js บรรทัด 156 ใช้
     'demo-tenant-001' เป็นค่า default เมื่อไม่มี tenantId
   - BookingModal.vue บรรทัด 272 ใช้ 'tenant-anon' (คนละค่ากัน ไม่สม่ำเสมอ)
   แนะนำ: ถ้าไม่มี uid จริงต้องไม่อนุญาตให้จอง และไม่ส่งแจ้งเตือน

C4 [วิกฤต] Admin กด "บันทึกผัง" อาจเขียนทับการจองของลูกค้า (Lost update)
   - saveMarketLayoutToFirestore() เขียน array stalls ทั้งก้อนจาก state ในเครื่อง admin
   - ระหว่างที่ admin กำลังแก้ ถ้ามีลูกค้าจองแผง X ลงไป แล้ว snapshot มาตอน isSaving = true
     (marketStore.js บรรทัด 170 ข้าม snapshot) หรือ admin ยังถือ state เก่าอยู่
     -> การจองของลูกค้าถูกเขียนทับเป็น 'available'
   - การจองใช้ transaction แต่การ save ผังไม่ใช้ -> transaction ฝั่งจองไม่ได้ช่วยอะไร

C5 [สูง] Snapshot ใหม่จาก Firestore เขียนทับงานที่ admin ยังไม่ได้บันทึก
   - marketStore.js บรรทัด 172-183: ทุก snapshot แทนที่ this.stalls ทั้งหมด และตั้ง
     hasUnsavedChanges = false + capture snapshot ใหม่
   -> admin กำลังลากแผงอยู่ แล้วมีลูกค้าจองแผงอื่น = งานที่ลากไว้หายหมดโดยไม่มีการเตือน
   แนะนำ (ทั้ง C4/C5): แยก stalls เป็น collection stalls/{stallId} (rules ก็เตรียมไว้แล้ว
   แต่ไม่ได้ใช้), บันทึกเฉพาะแผงที่เปลี่ยน (dirtyStallsMap มีอยู่แล้วแต่ไม่ได้ใช้),
   และ merge snapshot ระดับรายแผงแทนการแทนที่ทั้ง array

C6 [สูง] การจองเขียน zones ของฝั่งลูกค้าทับลง Firestore
   firebaseService.js บรรทัด 165-170: transaction.set(... zones: sanitizedZones ...)
   -> ถ้า client ของลูกค้ามี zones เก่า (จาก localStorage) จะเขียนทับ zones ล่าสุดของ admin
   แนะนำ: ใน transaction ให้อัปเดตเฉพาะแผงที่จอง ไม่ต้องส่ง name/zones

C7 [สูง] บันทึกการจองล้มเหลวแต่ UI แจ้งว่าสำเร็จ
   - saveLayoutToFirestore(): ถ้า Firestore error (res.success = false, ไม่ใช่ permission-denied)
     จะไปตก else แจ้ง "✅ บันทึกผังตลาดเรียบร้อยแล้ว" (marketStore.js บรรทัด 605-606)
   - catch บรรทัด 609-614 ก็แจ้ง success และตั้ง hasUnsavedChanges = false
   -> ผู้ใช้คิดว่าบันทึกแล้วแต่จริง ๆ ไม่ได้บันทึก
   - _sendBatchShiftNotifications() ถูกเรียก "ก่อน" save -> ถ้า save ล้มเหลว ผู้เช่าได้รับ
     แจ้งเตือนเรื่องที่ไม่ได้เกิดขึ้นจริง ควรส่งหลัง save สำเร็จ

C8 [สูง] StallEditorModal / ObjectEditorModal แสดงข้อมูลเก่า และกดบันทึกแล้วย้อนตำแหน่ง
   - watch(() => props.stallId) (StallEditorModal.vue) ทำงานเฉพาะตอน id เปลี่ยน
   - ขั้นตอนทำซ้ำ: เลือกแผง A -> เปิดแก้ไข -> ปิด -> ลากแผง A ไปที่ใหม่ -> เปิดแก้ไขอีกครั้ง
     -> ฟอร์มยังแสดงตำแหน่งเดิม -> กดบันทึก = แผงกระโดดกลับที่เดิม
   - ObjectEditorModal.vue มีปัญหาเดียวกัน
   แนะนำ: watch [() => props.isOpen, () => props.stallId] แล้วโหลดฟอร์มใหม่ทุกครั้งที่เปิด

C9 [กลาง] การปัดเศษเมตร 1 ตำแหน่งทำให้ขนาดแผงเพี้ยนเมื่อบันทึกจาก modal

===============================================================================
 D. ระบบจอง / Business logic ที่ยังขาด
===============================================================================

D1 [สูง] การจองไม่มี "วันที่" หรือ "ช่วงเวลา"
   - ราคาเป็น ฿/วัน แต่จองแล้วแผงเป็น 'booked' ถาวร ไม่มีวันเริ่ม/สิ้นสุด
   - ตลาดนัดปกติจองเป็นรายวัน/รายสัปดาห์ ควรมี bookings ที่ผูกกับ stallId + date
     และสถานะแผงคำนวณตามวันที่เลือก

D2 [สูง] สลิปโอนเงินไม่ถูกเก็บจริง และการจองยืนยันทันที
   - BookingModal อ่านรูปเป็น base64 แล้วส่ง slipUrl แต่ bookStallWithTransaction ไม่ได้บันทึก
     (ดีแล้วที่ไม่เก็บ base64 ลง Firestore เพราะจะเกิน 1MB) -> สลิปหาย ตรวจสอบย้อนหลังไม่ได้
   - สถานะเปลี่ยนเป็น 'booked' ทันทีโดยไม่มี admin ตรวจสลิป
     (มีสถานะ 'pending' เขียนไว้ใน comment ของ types/market.js แต่ไม่ได้ใช้)
   แนะนำ: อัปโหลดไป Firebase Storage, ตั้งสถานะ pending -> admin อนุมัติ -> booked
   และจำกัดขนาด/ชนิดไฟล์

D3 [กลาง] เลขบัตรประชาชนบังคับกรอกในฟอร์มจอง แต่ไม่ถูกส่งไปบันทึก
   (BookingModal บรรทัด 253 ตรวจ แต่ firebaseService ไม่ได้เก็บ) -> เก็บข้อมูลเกินจำเป็น
   ถ้าไม่ใช้ ควรเอาออก ถ้าใช้ต้องมีเหตุผลและแจ้งความยินยอมตาม PDPA

D4 [กลาง] ปุ่มยืนยันจองไม่มี loading/disabled -> กดซ้ำได้หลายครั้ง
   (BookingModal.vue บรรทัด 178-184)

D5 [กลาง] ตรวจสอบข้อมูลเฉพาะฝั่ง client
   rules ฝั่ง bookings ตรวจแค่ customerName != null และ stallId != null
   ไม่ตรวจว่า stall ว่างจริง / ราคา / ผู้จองเป็นคนเดียวกับ request.auth.uid

D6 [ต่ำ] เลข PromptPay '081-999-8888' hardcode ใน BookingModal บรรทัด 124
   ควรเป็นค่าตั้งค่าของตลาด (เก็บใน markets doc)

D7 [ต่ำ] "รายได้รวม" = ผลรวมราคา/วัน ของแผงที่ booked ไม่ได้สะท้อนรายได้จริง
   (ไม่มีจำนวนวัน, ไม่สนใจสถานะการชำระเงิน)

D8 [ต่ำ] ผังรองรับตลาดเดียว: hardcode doc id 'markets/main-layout' ในหลายที่

 E. ประสิทธิภาพ

E1 [กลาง] persistToLocal() ถูกเรียกทุก mousemove ระหว่างลาก/ย่อขยาย
   (updateStallPosition/Size, updateLayoutObjectPosition/Size)
   -> JSON.stringify ข้อมูลทั้งผัง 8 ครั้งต่อ event ทำให้ลากกระตุกเมื่อแผงเยอะ
   แนะนำ: บันทึกตอน mouseup หรือ debounce

E2 [กลาง] class transition-all duration-200 บนแผง/วัตถุขณะลาก -> ตำแหน่งตามเมาส์ช้า (lag)
   แนะนำ: ปิด transition ระหว่าง isDragging

E3 [กลาง] onSnapshot ของ notifications ดึงทั้ง collection โดยไม่ query/limit
   (import query, orderBy, limit มาแล้วแต่ไม่ได้ใช้) แล้วค่อยตัดเหลือ 30 ใน client
   แนะนำ: query(collection, where('tenantId','==',uid), orderBy('createdAt','desc'), limit(30))
   และเพิ่ม composite index ใน firestore.indexes.json

E4 [กลาง] เก็บทุกแผงใน document เดียว -> จำกัด 1MB, ทุกการจองต้องเขียนทั้ง document
   (contention สูงเมื่อมีคนจองพร้อมกันหลายคน transaction จะ retry/ล้มบ่อย)

E6 [กลาง] ผลทดสอบ build (vite build ไปที่โฟลเดอร์ชั่วคราว): build ผ่าน แต่ JS bundle เดียว
   ขนาด 723.85 kB (gzip 180 kB) เกินเกณฑ์ 500 kB
   แนะนำ: lazy-load modal ต่าง ๆ ด้วย defineAsyncComponent, แยกหน้า admin ด้วย route-level
   code splitting, ไม่โหลด firebase/analytics ถ้าไม่ใช้

E7 [กลาง] npm audit (เฉพาะ production deps) พบช่องโหว่ 11 รายการ (high 5, moderate 6)
   และ dependency หลายตัวตามหลังเวอร์ชันล่าสุดหลาย major (firebase 10 -> 12, vite 5 -> 8,
   pinia 2 -> 4, tailwind 3 -> 4) ควรวางแผนอัปเกรดทีละตัวและทดสอบ

E5 [ต่ำ] Navbar บรรทัด 180: ปุ่มบันทึกใช้ animate-pulse ตลอดเวลาที่มีการแก้ไข รบกวนสายตา
