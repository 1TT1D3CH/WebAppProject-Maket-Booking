# Prompt: ระบบตรวจสลิปก่อนยืนยันการจอง (admin / owner ตรวจจากรูป)

ใช้กับ repo "Dynamic Market Stall Booking System" (Vue 3 + Pinia + Vite + Tailwind + Firebase)

## เป้าหมาย

ผู้เช่าแนบรูปสลิปตอนกดจอง การจองจะเป็น **"รอตรวจสลิป"** และแผงถูกกันไว้
admin หรือ owner เปิดดูรูปสลิปเทียบกับยอดที่ต้องได้รับ แล้วกด **อนุมัติ / ขอสลิปใหม่ / ปฏิเสธ**
ผู้เช่าเห็นผลทันทีโดยไม่ต้อง refresh ใช้งานตรวจได้ทั้งบนมือถือ iPad และคอม

## วิธีใช้

1. เปิด coding agent ที่ root ของ repo วาง **"ส่วนหัว"** ตามด้วย prompt ของส่วนนั้น **ทีละส่วน ตามลำดับ**
2. ส่วน 0 agent จะขอให้คุณ copy rules ที่ใช้อยู่จริงจาก Firebase Console มาวาง (เพื่อไม่ให้ rules กับโค้ดไม่ตรงกันซ้ำรอยวันที่ 10 ต.ค.)
3. agent commit ให้ทีละส่วน แต่ **ไม่ push ไม่ deploy** จนกว่าคุณสั่ง ส่วน 4 จะเตรียมคำสั่ง deploy ไว้ให้

| ส่วน | เรื่อง | หยุดถามก่อนไหม |
|---|---|---|
| 0 | สำรวจโค้ดจริง + เทียบ rules + เสนอแผน | **ใช่** |
| 1 | แนบสลิปตอนจอง + สถานะ "รอตรวจสลิป" + rules ฝั่งผู้เช่า | ไม่ |
| 2 | หน้าตรวจสลิปของ admin/owner (มือถือ / iPad / คอม) + rules ฝั่ง admin | ไม่ |
| 3 | ฝั่งผู้เช่า: ดูสถานะ, ส่งสลิปใหม่, แจ้งเตือน | ไม่ |
| 4 | ทดสอบรวม + เตรียม deploy rules กับโค้ดพร้อมกัน | ไม่ (แต่ไม่ deploy เอง) |

### เรื่องที่เลือกไว้ให้แล้ว (บอก agent ได้ถ้าอยากเปลี่ยน)

- **เก็บสลิปใน Firestore เป็นรูปที่บีบอัดแล้ว (ไม่เกินราว 500 KB)** เพราะ Cloud Storage ต้องใช้ Blaze plan
  เขียนโค้ดให้สลับไป Storage ได้ภายหลังด้วยค่า env ตัวเดียว
- **แนบสลิปตอนกดจองเลย** ไม่มีการกันแผงแบบหมดเวลา แผงถูกกันไว้จนกว่า admin/owner จะตัดสิน
- **admin และ owner ตรวจได้เท่ากัน** (ใช้ `isAdmin()` เดิมที่รวม owner อยู่แล้ว) บันทึกว่าใครเป็นคนตัดสิน
- **ตรวจด้วยตา ไม่มีระบบอ่านสลิปอัตโนมัติ** (ต้องใช้บริการภายนอก/ฝั่ง server) แต่มีตัวช่วยเตือน "สลิปซ้ำ"
- **การจองเก่าที่ไม่มีสลิป** ถือว่ายืนยันแล้ว ไม่ต้องย้ายข้อมูล
- **ยังไม่ทำ QR PromptPay** (อยู่ใน `gap-fixes-th.md` ส่วน 5) ใช้ข้อมูลการชำระเงินที่หน้าเว็บมีอยู่ตอนนี้ไปก่อน

### ไม่แตะ (มีงานอื่นดูอยู่)

ห้ามแก้โค้ดบันทึก/โหลดผัง (`saveLayoutToFirestore`, onSnapshot/โหลดผัง, การรวมผังตั้งต้นกับข้อมูล Firebase)
งานนั้นอยู่ใน `stall-save-fix-th.md` ถ้าระบบสลิปจำเป็นต้องแก้ตรงนั้น agent ต้องหยุดถามก่อน

## ส่วนหัว (ใช้ทุกส่วน)

```
คุณคือนักพัฒนา Vue 3 + Pinia + Vite + Tailwind + Firebase (Firestore, Auth, Hosting) ที่ทำงานใน repo
"Dynamic Market Stall Booking System" (ระบบจองแผงตลาด)

งานนี้: ระบบตรวจสลิป ผู้เช่าแนบรูปสลิปตอนจอง -> การจองเป็น "รอตรวจสลิป" และกันแผงไว้ ->

  prompt เก่า (gap-fixes-th.md ส่วน 3-7) เคยออกแบบไว้แต่ถูกย้อนทิ้ง ห้ามเดาว่ามีอะไรอยู่

- โปรเจกต์ใช้ Firebase Spark plan (ฟรี) ห้ามใช้ Cloud Functions, Cloud Storage, Extensions, Firestore TTL
- สิทธิ์: users/{uid}.role ใน rules มี isAdmin() = role in ['admin','owner'] และ isOwner()
  (ยืนยันจากไฟล์จริง) ทั้ง admin และ owner ตรวจสลิปได้

บทเรียนวันที่ 10 ต.ค. (สำคัญ):
rules ที่ deploy ไม่ตรงกับโค้ดที่ deploy ทำให้บันทึกผังไม่ได้ (Missing or insufficient permissions)

ดังนั้น rules ใน repo อาจไม่ตรงกับที่ใช้จริง ต้องเทียบก่อนแก้ (ส่วน 0) และ rules ใหม่ต้อง deploy

1. ทำเฉพาะงานในส่วนนี้ ห้าม refactor สิ่งที่ไม่เกี่ยว
2. ห้ามแก้โค้ดบันทึก/โหลดผัง: saveLayoutToFirestore, การโหลด/onSnapshot ของผัง, stallSync,
   การรวมผังตั้งต้น (default objects) กับข้อมูล Firestore งานนั้นมีอีกงานแก้อยู่
   ถ้าระบบสลิปจำเป็นต้องแตะ ให้หยุดอธิบายเหตุผลและถามผมก่อน
3. ข้อมูลและ logic ชุดเดียว: ฟังก์ชันอ่าน/เขียนการจองและสลิปอยู่ใน service/store เดียว
   หน้าจอมือถือ / iPad / คอม เรียกชุดเดียวกัน ถ้ามี useDevice() และ shell แยกอุปกรณ์
   (จาก device-versions-th.md) ให้ใช้ตามนั้น ถ้ายังไม่มีให้ทำ responsive โดยแยก component หน้าจอ
   แต่ใช้ composable ร่วม และห้ามสร้างระบบแยกอุปกรณ์ขึ้นมาเองในงานนี้
4. UI ภาษาไทย รองรับ dark mode, ปุ่มบนมือถือ/iPad สูง >= 44px, input font >= 16px,
   ใช้ 100dvh และ env(safe-area-inset-*), ใช้ BaseModal/component เดิมถ้ามี
5. ห้ามกลืน error เงียบ ให้ log และแสดงข้อความไทย แยก permission-denied ออกจากเน็ตหลุด
6. ห้ามเพิ่ม dependency ใหม่โดยไม่ถาม (บีบอัดรูปใช้ canvas ของ browser ได้เลย)
7. ก่อนทุก commit รัน npm run build และ npm run test:unit (ถ้ามี) ต้องผ่าน
   ถ้าแก้ firestore.rules ให้เพิ่ม test ของ rules และรัน npm run test:rules (หรือ emulator ที่ repo ใช้)
   ถ้ารันไม่ได้ให้บอกตรง ๆ ว่ายังไม่ได้รัน ห้ามบอกว่าผ่าน
8. commit ย่อย ข้อความขึ้นต้น "feat(slip): ..." / "fix(slip): ..." / "test(slip): ..."
9. ห้าม git push, ห้าม firebase deploy ทุกรูปแบบ, ห้าม force push / เขียนประวัติ git ใหม่,
   ห้ามรันสคริปต์ที่แก้หรือลบข้อมูลใน Firestore จริง จนกว่าผมสั่งเองในแชท
10. จบแต่ละส่วนสรุปเป็นตาราง: ข้อ | สถานะ | ไฟล์ที่แก้ | วิธีทดสอบ พร้อมผล build/test จริง
    และรายการสิ่งที่ผมต้องทำเอง

## ส่วน 0: สำรวจโค้ดจริง + เทียบ rules + เสนอแผน

```
ส่วน 0: สำรวจ ยังไม่แก้โค้ด

1) git status, git log -15 --oneline (ไฟล์ที่แก้ค้างและไม่ใช่ของงานนี้ ห้ามแตะ ให้บอกผม)
   รัน npm ci (ถ้ายังไม่ติดตั้ง), npm run build, npm run test:unit, npm run test:rules จดผลเป็นค่าตั้งต้น

2) ไล่ขั้นตอนจองตอนนี้ตั้งแต่ BookingModal จนถึง Firestore แล้วตอบ:
   - แผงเก็บที่ไหน: array ใน markets/{id} หรือ subcollection markets/{id}/stalls/{sid}
   - การจองเขียนอะไรบ้าง (stall.status, bookedBy, bookings/{id}) ใน transaction/batch เดียวกันไหม
   - ฟิลด์จริงของ bookings ตอนนี้ และมี status / dates / bookingLocks แล้วหรือยัง
   - มีช่องแนบสลิปอยู่แล้วไหม รูปไปไหน (รายงานเก่าบอกว่า "อัปโหลดแล้วทิ้ง")
   - ข้อมูลการชำระเงิน (เบอร์ PromptPay/บัญชี) แสดงจากไหน
   - มีหน้า "การจองของฉัน" / หน้าจัดการการจองของ admin / ระบบแจ้งเตือน (notifications) หรือยัง
   - มี useDevice() หรือ shell แยก phone/tablet/desktop แล้วหรือยัง เมนูหลักอยู่ไฟล์ไหน

3) ข้อที่ต้องตอบให้ชัด (เกี่ยวกับงานแก้บันทึกผังที่ทำคู่กันอยู่):
   - saveLayoutToFirestore เขียน status / bookedBy ของแผงทับไปด้วยไหม ถ้าใช่ แปลว่า admin กดบันทึกผัง
     แล้วการจองที่รอตรวจอาจถูกทับหาย ให้รายงานพร้อมไฟล์:บรรทัด ห้ามแก้เอง
   - ถ้าแผงเป็น array ใน doc ผัง การจองต้องเขียน doc เดียวกับที่ admin บันทึกผัง ให้ถือว่าชนกับงานนั้น
     และใช้แบบ "กันแผงแยก collection" ในข้อ 5

4) เทียบ rules:
   - ขอให้ผม copy rules ที่ใช้อยู่จริงจาก Firebase Console > Firestore > Rules มาวาง
     แล้วเก็บไว้ที่ docs/rules-deployed-2026-10-11.rules (ไฟล์นี้ commit ได้ ไม่มีความลับ)
   - diff กับ firestore.rules ใน repo แล้วสรุปว่าต่างตรงไหน ทางไหนเป็นของที่ใช้จริง
   - จุดที่รู้แล้ว: ใน Console ผมแก้ markets ให้ admin update ได้โดยไม่เช็ค revision
     (allow create, update, delete: if isAdmin();) ส่วนนี้ต้องคงไว้ในไฟล์ใหม่
   - ถ้าต่างกัน ให้ทำ commit แรกของงานนี้ = ปรับ firestore.rules ใน repo ให้ตรงกับที่ใช้จริงก่อน
     (เฉพาะที่จำเป็นให้โค้ดตอนนี้ทำงานได้) แล้วค่อยเพิ่ม rules ของสลิปทับในส่วนถัดไป

5) เสนอแผนโครงข้อมูล (ค่าเริ่มต้นด้านล่าง ปรับตามโค้ดจริงได้ บอกเหตุผล):

   สถานะการจอง (bookings/{id}.status):
     pending (รอตรวจสลิป) -> approved (อนุมัติ)
                          -> needs_slip (ขอสลิปใหม่ + เหตุผล, ยังกันแผงไว้) -> pending (ผู้เช่าส่งใหม่)
                          -> rejected (ปฏิเสธ + เหตุผล, ปล่อยแผง)
     pending / needs_slip -> cancelled (ผู้เช่ายกเลิกเอง, ปล่อยแผง)
     การจองเก่าที่ไม่มี status ให้แสดงเป็น "ยืนยันแล้ว" ไม่ต้องย้ายข้อมูล
   ฟิลด์ใหม่ใน booking: status, statusReason, amountDue (ยอดที่ต้องได้รับ ณ ตอนจอง),
     slipHash, slipUploadedAt, decidedBy, decidedAt, updatedAt

   การกันแผง เลือกตามที่พบ:
     ก. ถ้ามี bookingLocks (จองตามวันที่) แล้ว: ใช้ lock.status = pending / approved ตาม booking
     ข. ถ้าแผงอยู่ใน subcollection และการจองเขียน stall.status ผ่านเส้นทางจองของตัวเอง
        (ไม่ผ่าน saveLayoutToFirestore): เพิ่มสถานะแผง 'pending' (รอตรวจสลิป) คู่กับ 'booked'
     ค. ถ้าแผงเป็น array ใน doc ผัง หรือ saveLayoutToFirestore ทับ status ของแผง:
        เก็บการกันแผงแยกที่ stallHolds/{marketId}_{stallId} { marketId, stallId, bookingId,
        tenantId, status } ผังอ่าน collection นี้มาระบายสี โดยไม่แตะโค้ดบันทึก/โหลดผัง
     ระบุว่าเลือกข้อไหนเพราะอะไร

   สลิป: bookingSlips/{bookingId} { tenantId, marketId, dataUrl, mime, bytes, createdAt }
     แยก collection เพื่อไม่ให้รายการจองโหลดรูปมาด้วย
     src/services/slipStorage.js: saveSlip(bookingId, file) / getSlip(bookingId) / deleteSlip(bookingId)
     เลือก backend ด้วย VITE_SLIP_BACKEND ('firestore' ค่าเริ่มต้น, 'storage' สำหรับอนาคต
     ที่อัปเกรด Blaze: เตรียมโค้ดและ storage.rules ไว้ แต่ห้ามเพิ่ม "storage" ใน firebase.json)

   ตัวช่วยสลิปซ้ำ: slipHash = SHA-256 ของไฟล์ต้นฉบับ (crypto.subtle) เก็บใน booking
     หน้าตรวจค้น booking อื่นที่ slipHash เดียวกัน ถ้าเจอแสดงคำเตือนสีแดง (เตือนอย่างเดียว ไม่บล็อก)

   rules ที่จะเพิ่ม (ร่างเป็นข้อ ๆ) และ index ที่ต้องใช้

6) ภาพร่าง ASCII ของหน้าตรวจสลิป: มือถือ, iPad แนวตั้ง, iPad แนวนอน, คอม

แล้วหยุดรอผมตอบ "ตกลง"

## ส่วน 1: แนบสลิปตอนจอง + สถานะ "รอตรวจสลิป"

```
ส่วน 1: ฝั่งผู้เช่าตอนจอง ตามแผนที่ผมตกลงในส่วน 0

บีบอัดรูป (src/utils/compressImage.js):
- รับ jpg / png / webp; HEIC หรือไฟล์ที่อ่านไม่ได้ แสดง "รองรับเฉพาะรูป JPG, PNG, WebP"
  (บอกวิธีบน iPhone: แคปหน้าจอสลิปแทนการแนบไฟล์ HEIC)
- ย่อด้านยาวสุด 1600px แปลงเป็น webp (fallback jpeg) ลด quality ทีละขั้นจน dataUrl <= 700,000 ตัวอักษร
  ถ้ายังเกินให้ย่อขนาดภาพต่อ อย่าย่อจนตัวเลขบนสลิปอ่านไม่ออก (ด้านยาวไม่ต่ำกว่า ~900px)
- คำนวณ slipHash จากไฟล์ต้นฉบับก่อนบีบอัด
- unit test ส่วนที่ทดสอบได้ (ตรวจชนิดไฟล์, ขีดจำกัดขนาด, ฟังก์ชันคำนวณ quality/ขนาด)

BookingModal:
- แสดงยอดที่ต้องโอนตัวใหญ่ + ข้อมูลการชำระเงินที่มีอยู่เดิม
- ช่องแนบสลิป (บังคับ) รองรับถ่ายรูป/เลือกจากคลังบนมือถือ, แสดงรูปตัวอย่าง, ปุ่มเปลี่ยนรูป
- สถานะระหว่างบีบอัด/ส่ง ปุ่มกดซ้ำไม่ได้
- สำเร็จแล้วบอก "ส่งการจองแล้ว รอผู้ดูแลตรวจสลิป" ไม่ใช้คำว่า "จองสำเร็จ"

บันทึก:
- booking (status 'pending', amountDue, slipHash, slipUploadedAt) + การกันแผง (ตามแบบที่เลือก)
  + bookingSlips/{bookingId} เขียนใน transaction/batch เดียวกัน ถ้าส่วนไหนล้ม ต้องไม่มีอะไรค้าง
- แผงที่รอตรวจแสดงสีเหลือง "รอตรวจสลิป" บนผัง เพิ่มใน legend คนอื่นจองซ้อนไม่ได้
- ถ้าเลือกแบบ ข / ค ตรวจว่าเส้นทางเขียนนี้ไม่ผ่าน saveLayoutToFirestore

firestore.rules (ฝั่งผู้เช่า):
- booking create: tenantId == uid, ผู้ใช้ไม่ใช่ anonymous, status == 'pending',
  keys().hasOnly([...]), amountDue ตรงกับราคาแผงจริง (get/getAfter ของแผง ชื่อฟิลด์ตามจริง),
  แผงที่กันไว้ใน getAfter() ชี้ bookingId นี้และเป็นของ uid, createdAt == request.time
- การกันแผง: สร้างได้ต่อเมื่อแผงว่าง (ไม่มีคนจอง/รอตรวจอยู่) และ booking ใน getAfter() ชี้กลับมา
  ผู้เช่าตั้งสถานะเป็น approved / booked เองไม่ได้
- bookingSlips create: tenantId == uid, booking ใน getAfter() เป็นของ uid,
  dataUrl เป็น string ยาว < 750000 และ matches '^data:image/(webp|jpeg);base64,.*'
  read: เจ้าของ หรือ isAdmin(); delete: isAdmin()
- ตอนนี้โค้ดเก่าที่จองแบบ "booked ทันที" ต้องถูกปฏิเสธ (ข้อนี้เองที่ทำให้ต้อง deploy rules พร้อมโค้ด)

Test rules: จองพร้อมแนบสลิปผ่าน, จองโดยไม่มีสลิปไม่ผ่าน (ถ้า rules ตรวจได้ ไม่งั้นบอก),
ตั้ง status approved เองไม่ผ่าน, ปลอม amountDue ไม่ผ่าน, สองบัญชีจองแผงเดียวกันผ่านได้บัญชีเดียว,
แนบ dataUrl ที่ไม่ใช่รูปหรือใหญ่เกินไม่ผ่าน, บัญชีอื่นอ่านสลิปเราไม่ได้, anonymous จองไม่ได้
```

**ทดสอบ:** แนบรูปมือถือ 8 MB แล้วระบบย่อเหลือไม่เกิน ~500 KB และยังอ่านตัวเลขออก; แนบ PDF ไม่ได้;
จองแล้วอีกเครื่องเห็นแผงเป็นสีเหลืองทันที

## ส่วน 2: หน้าตรวจสลิปของ admin / owner

```
ส่วน 2: หน้า "ตรวจสลิป" สำหรับ isAdmin() (admin และ owner)

ข้อมูล (composable ร่วม useSlipReview):
- query bookings where status in ['pending'] orderBy createdAt asc (onSnapshot) + index
  แท็บ "รอตรวจ" (pending) / "ขอสลิปใหม่" (needs_slip) / "ตัดสินแล้ว" (approved/rejected ล่าสุด 50 รายการ)
- รูปสลิปโหลดเฉพาะตอนเปิดรายการนั้น (getSlip) และ prefetch รายการถัดไป 1 รายการ
- ตัวนับรายการรอตรวจเป็น badge บนเมนู (เห็นเฉพาะ admin/owner)

หน้ารายละเอียด (ข้อมูลที่ใช้ตัดสิน):
- รูปสลิป: แตะเพื่อเต็มจอ, pinch-zoom / ดับเบิลแตะซูมบนมือถือและ iPad, ล้อเมาส์ซูมบนคอม, หมุน 90°
- ข้าง/ใต้รูป: "ยอดที่ต้องได้รับ" ตัวใหญ่, ชื่อผู้รับเงินที่ตลาดตั้งไว้ (ถ้ามี), เวลาที่จอง,
  แผง/โซน, ชื่อผู้เช่า ชื่อร้าน เบอร์ (tel: link)
- checklist ให้ติ๊กด้วยตา (ไม่บันทึก แค่ช่วยไม่ให้ลืม): ยอดตรง / ชื่อผู้รับตรง / เวลาโอนหลังเวลาจอง /
  ไม่ใช่สลิปซ้ำ
- คำเตือนสีแดงถ้า slipHash ซ้ำกับ booking อื่น พร้อมลิงก์ไปดูรายการนั้น

ปุ่มตัดสิน:
- อนุมัติ -> approved (กันแผงเปลี่ยนเป็นจองแล้ว)
- ขอสลิปใหม่ (ต้องใส่เหตุผล มีตัวเลือกด่วน: "ยอดไม่ตรง", "รูปไม่ชัด", "ไม่ใช่สลิปของการจองนี้") -> needs_slip
- ปฏิเสธ (ต้องใส่เหตุผล) -> rejected + ปล่อยแผง
- ทุกปุ่มทำใน batch/transaction เดียว: booking (status, statusReason, decidedBy = uid, decidedAt,
  updatedAt) + การกันแผง + notification ถึงผู้เช่า (ถ้ามีระบบแจ้งเตือน)
- ถ้า booking ถูกคนอื่นตัดสินไปแล้ว (admin สองคนเปิดพร้อมกัน) ให้ transaction อ่านสถานะล่าสุด
  ถ้าไม่ใช่ pending แสดง "รายการนี้ถูกตรวจไปแล้วโดย ..." ไม่ทับ
- อนุมัติแล้วไปรายการถัดไปอัตโนมัติ (ตรวจต่อเนื่องได้เร็ว)

หน้าตาตามอุปกรณ์ (logic เดียวกัน):
- มือถือ: รายการเป็นการ์ด แตะแล้วเปิดหน้ารายละเอียดเต็มจอ รูปสลิปอยู่บน ข้อมูลอยู่ใต้รูป
  ปุ่มตัดสินเป็นแถบติดล่าง (sticky + safe-area-bottom) ปุ่ม "อนุมัติ" กว้างสุด
  ปัดซ้าย/ขวาหรือปุ่ม ‹ › ไปรายการก่อน/ถัดไป
- iPad แนวนอน: แบ่ง 2 ฝั่ง รายการซ้าย (~320px) รายละเอียดขวา รูปสลิปกับยอดเงินเห็นพร้อมกันโดยไม่ต้องเลื่อน
- iPad แนวตั้ง: รายการเต็มจอ แตะแล้วรายละเอียดเลื่อนขึ้นมา รูปด้านบน ข้อมูล+ปุ่มด้านล่าง
- คอม: ตาราง + แผงรายละเอียดด้านขวา, คีย์ลัด A = อนุมัติ, R = ขอสลิปใหม่, J/K = ถัดไป/ก่อนหน้า
  (ไม่ทำงานตอนพิมพ์ในช่องข้อความ)
- ถ้ามี shell แยกอุปกรณ์อยู่แล้ว ให้ใส่เมนู "ตรวจสลิป" ในทุก shell สำหรับ admin/owner

firestore.rules (ฝั่ง admin):
- isAdmin() เปลี่ยน status ได้ตาม state machine เท่านั้น: pending -> approved / needs_slip / rejected
- ห้ามแก้ tenantId, amountDue, slipHash, ข้อมูลแผง/วันที่; ต้องมี decidedBy == uid, decidedAt == request.time
- statusReason บังคับเมื่อ needs_slip / rejected (string 1..300 ตัว)
- การกันแผงต้องเปลี่ยนตาม booking ใน getAfter() (approved -> จองแล้ว, rejected -> ปล่อย)
- ผู้เช่าเปลี่ยนเป็น approved เองไม่ได้

Test rules: tenant อนุมัติเองไม่ได้, admin แก้ยอดเงินไม่ได้, admin เปลี่ยน approved -> pending ไม่ได้,
ปฏิเสธโดยไม่ใส่เหตุผลไม่ได้, owner อนุมัติได้เหมือน admin, tenant อ่านสลิปคนอื่นไม่ได้แต่ admin อ่านได้
```

**ทดสอบ:** บน iPhone เปิดรายการรอตรวจ ซูมดูตัวเลขบนสลิปได้ชัด แล้วกดอนุมัติด้วยนิ้วโป้งได้;
บน iPad แนวนอนเห็นรูปและยอดเงินพร้อมกัน; admin สองเครื่องกดตัดสินรายการเดียวกัน ผลไม่ทับกัน;
ปฏิเสธแล้วแผงกลับว่างบนผังทันที

## ส่วน 3: ฝั่งผู้เช่า ดูสถานะ / ส่งสลิปใหม่ / แจ้งเตือน

```
ส่วน 3: ผู้เช่าเห็นผลการตรวจและแก้ไขได้

- ถ้ามีหน้า "การจองของฉัน" แล้วให้เพิ่มลงไป ถ้ายังไม่มีให้ทำแบบเรียบง่าย:
  query bookings where tenantId == uid orderBy createdAt desc (onSnapshot) + index
  การ์ด: แผง, โซน, ยอด, badge สถานะไทย (รอตรวจสลิป / ขอสลิปใหม่ + เหตุผล / อนุมัติแล้ว /
  ถูกปฏิเสธ + เหตุผล / ยกเลิกแล้ว / ยืนยันแล้ว สำหรับการจองเก่า)
  รายละเอียดแสดงรูปสลิปของตัวเอง (โหลดเมื่อเปิด)
- needs_slip: ปุ่ม "ส่งสลิปใหม่" ใช้ตัวบีบอัดเดิม -> update bookingSlips + booking กลับเป็น pending
  (ล้าง statusReason, อัปเดต slipHash, slipUploadedAt) ใน batch เดียว
  rules: เจ้าของเปลี่ยน needs_slip -> pending ได้ แก้ได้เฉพาะฟิลด์เหล่านี้ และ update bookingSlips ได้
  เฉพาะตอน booking เป็น needs_slip
- ยกเลิกเอง: ได้เฉพาะ pending / needs_slip, dialog ยืนยัน, ปล่อยแผงใน batch เดียวกัน
  การจองที่ approved แล้วแสดง "ติดต่อผู้ดูแลตลาดเพื่อยกเลิก"
  rules: เจ้าของเปลี่ยนเป็น cancelled ได้จาก pending / needs_slip เท่านั้น
- แจ้งเตือน: ถ้ามีระบบ notifications อยู่ ให้แสดงผลอนุมัติ / ขอสลิปใหม่ / ปฏิเสธ แบบ realtime
  (ใช้ tenantId == uid จริง ไม่มีค่า demo) ถ้ายังไม่มีระบบ ให้ใช้ badge บนเมนู "การจองของฉัน" แทน
  ห้ามสร้างระบบแจ้งเตือนใหม่ทั้งระบบในงานนี้
- หน้าจอ: ทำงานดีบนมือถือ (การ์ดเต็มความกว้าง, ปุ่มส่งสลิปใหม่ใหญ่) และ iPad ตามกติกาส่วนหัว

Test rules: ส่งสลิปใหม่ตอน pending/approved ไม่ได้, ยกเลิก booking คนอื่นไม่ได้,
ยกเลิกที่ approved แล้วไม่ได้, แก้ amountDue ตอนส่งสลิปใหม่ไม่ได้
```

**ทดสอบ:** admin กด "ขอสลิปใหม่" แล้วมือถือผู้เช่าเห็นเหตุผลทันที ส่งรูปใหม่แล้วกลับไปอยู่ในแท็บ "รอตรวจ" ของ admin
