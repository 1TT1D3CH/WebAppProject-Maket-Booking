> **สถานะการใช้งาน (อัปเดตทุกครั้งที่จบส่วน เพื่อป้องกันการรันซ้ำ)**
>
> | ส่วน | สถานะ | commit |
> |---|---|---|
> | 0 สำรวจ + วันที่เขตเวลาไทย | ✅ ใช้แล้ว — ห้ามรันซ้ำ | `b444ebb` |
> | 1 ลืมรหัสผ่าน | ✅ ใช้แล้ว — ห้ามรันซ้ำ | `837dba3` |
> | 2–7 | ⏳ รอ `fix-prompts-th.md` ระยะ 2–3 ก่อน | – |

ฟีเจอร์ในไฟล์นี้มาจาก `feature-checklist-th.md` กลุ่ม P0 ที่ยังไม่มี prompt

วิธีใช้
1. ทำ `fix-prompts-th.md` ระยะ 1 ถึง 3 ให้จบก่อน เพราะ prompt นี้ต่อยอดจาก rules, collection `bookings`
   และสถานะการจองที่ทำไว้ในระยะนั้น
2. เปิด AI coding agent ที่ root ของ repo วาง **"ส่วนหัว"** ตามด้วย prompt ของส่วนนั้น ทีละส่วน ตามลำดับ
3. จบแต่ละส่วน ลองตามขั้นตอนทดสอบท้ายส่วน แล้วค่อยเริ่มส่วนถัดไป

| ส่วน | เรื่อง | ต้องหยุดถามแผนก่อนไหม |
|---|---|---|
| 0 | สำรวจโค้ด + วันที่เขตเวลาไทย | ไม่ |
| 1 | ลืมรหัสผ่าน | ไม่ |
| 2 | ตั้งวันเปิด-ปิดตลาด | ไม่ |
| 3 | หมดเวลาชำระเงินแล้วปล่อยแผงคืน | **ใช่** (เปลี่ยนสถานะการจอง) |
| 4 | หน้า "การจองของฉัน" | ไม่ |
| 5 | ค้นหาและกรองการจองในหน้า admin | ไม่ |
| 6 | owner จัดการสิทธิ์ผู้ใช้ | ไม่ |
| 7 | ยอมรับกติกา + นโยบายความเป็นส่วนตัว (PDPA) | ไม่ แต่ต้องกรอกเนื้อหาเอง |

> ส่วน 7 agent จะสร้างหน้าและโครงข้อความให้ แต่ข้อมูลจริง (ชื่อผู้ให้บริการ ช่องทางติดต่อ ระยะเวลาเก็บข้อมูล)
> คุณต้องกรอกเอง และถ้าเปิดให้คนทั่วไปใช้ ควรให้ผู้รู้กฎหมายช่วยดูข้อความอีกครั้ง

## ส่วนหัว (ใช้ทุกส่วน)

```
คุณคือนักพัฒนา Vue 3 + Pinia + Firebase (Firestore, Auth, Storage) ที่ทำงานใน repo
"Dynamic Market Stall Booking System"

บริบท:
- แก้ไขตาม code review ระยะ 1 ถึง 3 เสร็จแล้ว (ตรวจ git log และ docs/booking-design.md, docs/data-model.md ถ้ามี)
  ได้แก่ firestore.rules ที่เช็ค role จาก users/{uid}, การจองรายวันใน collection bookings
  (doc id แบบ `${stallId}_${yyyy-mm-dd}`), สลิปใน Firebase Storage และสถานะ pending/approved/rejected/cancelled
- ถ้าโค้ดจริงต่างจากที่ prompt นี้อธิบาย ให้ยึดโค้ดจริง ปรับวิธีทำให้เข้ากัน และบอกผมในสรุปว่าต่างตรงไหน

กติกาการทำงาน:
1. ทำเฉพาะงานในส่วนนี้ ห้ามขยายขอบเขต ห้าม refactor สิ่งที่ไม่เกี่ยวข้อง
2. commit ย่อย ข้อความขึ้นต้นด้วย feat/fix และรหัสส่วน เช่น "feat(P0-2): ตั้งวันหยุดตลาด"
3. หลังแต่ละ commit รัน `npm run build` ต้องผ่าน ถ้ามี lint/test ให้รันด้วย
   ถ้าแก้ firestore.rules และมี emulator ให้เพิ่ม test ของ rules ที่เกี่ยวข้อง
4. ห้ามทำสิ่งที่ย้อนกลับไม่ได้โดยไม่ถามก่อน: `firebase deploy`, ลบ/ย้ายข้อมูลจริงใน Firestore,
   force push, อัปเกรด dependency แบบ major ให้เตรียมไฟล์แล้วบอกคำสั่งให้ผมรันเอง
5. สิ่งที่ต้องแก้ใน Firebase Console หรือต้องสร้าง index ให้ใส่ใน firestore.indexes.json
   และสรุปเป็นขั้นตอนให้ผมทำ
6. ข้อความ UI เป็นภาษาไทย ใช้สไตล์และ component เดิม (รวม BaseModal ถ้ามีแล้ว) รองรับ dark mode และมือถือ
7. จบงานให้สรุป: ทำอะไรไป, ไฟล์ที่แก้, สิ่งที่ผมต้องทำเอง, วิธีทดสอบ
```

## ส่วน 0: สำรวจโค้ด และวันที่เขตเวลาไทย

```
ส่วน P0-0: สำรวจ และทำให้วันที่ใช้เขตเวลาไทยสม่ำเสมอ

1) สำรวจแล้วสรุปให้ผมก่อน (ยังไม่ต้องแก้):
   - โครงสร้าง document ของ bookings, stalls, markets, users ตอนนี้มีฟิลด์อะไร
   - สถานะการจองที่ใช้จริงมีค่าอะไรบ้าง และเปลี่ยนสถานะที่ไฟล์ไหน
   - ขั้นตอนจองตอนนี้: สร้าง booking ตอนไหน อัปโหลดสลิปตอนไหน (พร้อมกันหรือแยกขั้น)
   - มี vue-router แล้วหรือยัง (ส่วนถัด ๆ ไปจะเพิ่มหน้าใหม่)
   - วันที่การจองเก็บเป็น string 'yyyy-mm-dd' หรือ Timestamp และสร้างจาก new Date() ตรงไหนบ้าง

2) วันที่เขตเวลาไทย:
   - สร้าง src/utils/date.js รวมฟังก์ชันวันที่ทั้งหมด โดยยึดเขตเวลา 'Asia/Bangkok' เสมอ
     ไม่ขึ้นกับเขตเวลาของเครื่องผู้ใช้:
     todayBangkok() -> 'yyyy-mm-dd', toDateKey(date), fromDateKey(key), addDays(key, n),
     dayOfWeek(key) (0=อาทิตย์ ... 6=เสาร์), formatThaiDate(key) เช่น "ส. 12 ต.ค. 2569"
     ใช้ Intl.DateTimeFormat ('th-TH', timeZone 'Asia/Bangkok') ไม่ต้องเพิ่ม library ถ้าไม่จำเป็น
   - แทนที่การสร้าง/แปลงวันที่แบบกระจายในโค้ดด้วยฟังก์ชันเหล่านี้
     ระวังบั๊กแบบ new Date('2026-10-12') ที่ได้เวลา UTC แล้ววันเลื่อน
   - ถ้ามี Vitest แล้ว เขียน test ของ date.js รวมกรณีเวลา 23:30 และ 00:30 ตามเวลาไทย

ทดสอบ: เปลี่ยนเขตเวลาเครื่องเป็น UTC หรือ America/New_York แล้วเปิดหน้าจอง -> วันที่ "วันนี้"
และวันที่ในการจองต้องตรงกับเวลาไทย
```

## ส่วน 2: ตั้งวันเปิด-ปิดตลาด

```
ส่วน P0-2: ตั้งวันเปิด-ปิดตลาด และกันจองวันที่ตลาดไม่เปิด

ข้อมูล (เพิ่มใน markets/{marketId} ในฟิลด์ settings หรือ doc ตั้งค่าเดิมถ้ามีแล้ว):
- openWeekdays: array ของเลขวัน 0-6 (เช่น [5,6,0] = ศุกร์ เสาร์ อาทิตย์)
- closedDates: array ของ 'yyyy-mm-dd' วันหยุดพิเศษ (เช่น ฝนตก งานซ่อม)
- extraOpenDates: array ของ 'yyyy-mm-dd' วันเปิดพิเศษนอกวันปกติ (เช่น วันหยุดยาว)
- maxAdvanceDays: จองล่วงหน้าได้สูงสุดกี่วัน (ค่าเริ่มต้น 30)
- bookingCutoffTime: 'HH:mm' เวลาปิดรับจองของวันก่อนวันขาย (ค่าเริ่มต้น '20:00') ถ้าว่างคือไม่จำกัด
- ถ้า doc ยังไม่มีฟิลด์เหล่านี้ ให้ถือว่าเปิดทุกวัน (ไม่ทำให้ตลาดเดิมพัง)

ฟังก์ชันกลาง src/utils/marketCalendar.js:
- isMarketOpen(settings, dateKey) และ canBookDate(settings, dateKey, now) คืนค่า { ok, reason }
  reason เป็นข้อความไทย เช่น "ตลาดไม่เปิดวันนี้", "ปิดรับจองวันนี้แล้ว", "จองล่วงหน้าได้ไม่เกิน 30 วัน"
- ใช้ฟังก์ชันวันที่จาก src/utils/date.js เท่านั้น

หน้า admin:
- หน้าหรือ modal "ตั้งค่าตลาด" (รวมกับที่ตั้งเลข PromptPay ในระยะ 3 ถ้ามี)
  เลือกวันเปิดประจำสัปดาห์เป็นปุ่ม จ-อา, ปฏิทินเลือกวันหยุดพิเศษ/วันเปิดพิเศษพร้อมใส่หมายเหตุสั้น ๆ,
  ช่อง maxAdvanceDays และ bookingCutoffTime
- ถ้าตั้งวันหยุดพิเศษในวันที่มีการจอง approved หรือ pending อยู่แล้ว: เตือนจำนวนการจองที่กระทบ
  และถามยืนยัน ห้ามยกเลิกการจองอัตโนมัติ (ให้ admin ไปจัดการเองในส่วน 5)

หน้าลูกค้า:
- date picker ปิดวันที่จองไม่ได้ (เทา + tooltip เหตุผล) และค่าเริ่มต้นเป็นวันเปิดถัดไปที่จองได้
- ถ้าเลือกวันที่ตลาดปิด ผังแสดงข้อความ "ตลาดไม่เปิดวันที่เลือก" แทนการให้กดจอง

firestore.rules:
- ตอนสร้าง booking ให้ get() markets doc แล้วตรวจอย่างน้อย: วันที่ไม่อยู่ใน closedDates และ
  ไม่เกิน maxAdvanceDays ถ้าตรวจวันในสัปดาห์ได้ (เช่นเก็บ dayOfWeek ใน booking แล้วตรวจกับวันที่)
  ให้ตรวจด้วย ถ้าข้อไหนตรวจใน rules ไม่ได้ ให้บอกผมว่าข้อไหน และทำไว้ฝั่ง client
- settings แก้ได้เฉพาะ isAdmin()

ทดสอบ: ตั้งเปิดเฉพาะเสาร์-อาทิตย์ -> วันธรรมดาเลือกไม่ได้; ตั้งวันหยุดพิเศษ -> จองวันนั้นไม่ได้
ทั้งจาก UI และจากการยิง Firestore ตรง (ถ้ามี emulator test); จองล่วงหน้าเกินกำหนดไม่ได้

## ส่วน 3: หมดเวลาชำระเงินแล้วปล่อยแผงคืน

```
ส่วน P0-3: กันแผงไว้ระหว่างชำระเงิน และปล่อยคืนเมื่อหมดเวลา

ปัญหา: ถ้าลูกค้ากดจองแล้วไม่ส่งสลิป แผงจะถูกล็อกไว้ตลอด หรือถ้าไม่ล็อกเลย คนสองคนจะโอนเงินแผงเดียวกัน

ก่อนเขียนโค้ด ให้เขียนแผนใน docs/payment-hold.md แล้วหยุดถามผม โดยใช้แนวทางนี้เป็นค่าเริ่มต้น:
- สถานะใหม่ 'hold' (กันไว้รอชำระ) พร้อม holdExpiresAt = เวลาสร้าง + 15 นาที
  (ตั้งค่าได้ใน settings.paymentHoldMinutes)
- ลำดับ: ลูกค้ากด "จอง" -> สร้าง booking สถานะ 'hold' ด้วย transaction -> แสดง QR และนับถอยหลัง
  -> อัปโหลดสลิปทันเวลา -> เปลี่ยนเป็น 'pending' (รอ admin ตรวจ)
  ถ้าตอนนี้โค้ดสร้าง booking พร้อมสลิปในขั้นเดียว ให้เสนอวิธีแยกขั้นในแผน
- ปล่อยแผงคืนแบบไม่ต้องใช้ Cloud Functions (ใช้ได้กับ Spark plan ฟรี):
  * ถือว่า booking ที่ status == 'hold' และ holdExpiresAt < ตอนนี้ คือ "หมดเวลา" = แผงว่าง
    ทั้งตอนแสดงผัง และตอนเช็คใน transaction จอง
  * rules: อนุญาตให้ผู้ใช้คนใหม่เขียนทับ doc `${stallId}_${date}` ได้ เฉพาะเมื่อ doc เดิม
    เป็น 'hold' ที่ holdExpiresAt < request.time หรือสถานะ 'rejected' / 'cancelled' / 'expired'
    (ข้อนี้ทำให้แผงที่ถูกปฏิเสธหรือยกเลิกกลับมาจองได้ด้วย ถ้าระยะ 3 ยังไม่ได้ทำ)
  * ก่อนเขียนทับ ให้เก็บประวัติของ booking เดิมไว้ (เช่น คัดลอกไป bookingHistory/{autoId})
    เพื่อไม่ให้ประวัติการจองหายจากหน้า "การจองของฉัน" ของคนเดิม
  * rules: เปลี่ยน 'hold' -> 'pending' ได้เฉพาะเจ้าของ และต้องก่อน holdExpiresAt และต้องมี slipPath
  * holdExpiresAt ต้องตั้งจาก request.time ใน rules ตรวจ (ห้ามเชื่อเวลาจาก client)
- ทางเลือกเสริม (เขียนแยกในแผน ไม่ต้องทำถ้าผมไม่ตอบรับ): Cloud Function แบบ scheduled ทุก 5 นาที
  เปลี่ยน hold ที่หมดเวลาเป็น 'expired' และส่งแจ้งเตือน ต้องใช้ Blaze plan
- จำกัด hold พร้อมกันได้ไม่เกิน 3 แผงต่อผู้ใช้ (กันคนกดกันแผงเล่น) ถ้าตรวจใน rules ไม่ได้ให้บอก

หลังผมตกลงแผน:
- UI: นับถอยหลังบนหน้าชำระเงิน "กรุณาส่งสลิปภายใน 14:59" เมื่อหมดเวลาให้แจ้ง
  "หมดเวลาชำระเงิน แผงถูกปล่อยให้คนอื่นจองแล้ว" และปิดปุ่มส่งสลิป
- ผัง: แผงที่มี hold ยังไม่หมดเวลา แสดงสถานะ "มีคนกำลังจอง" (สีต่างจากจองแล้ว) กดจองไม่ได้
- หน้า admin: ไม่ต้องแสดง hold ในรายการรออนุมัติ
- รายได้/รายงานไม่นับ hold และ expired
- แก้ JSDoc typedef ของ Booking และ docs ให้มีสถานะใหม่

ทดสอบ: จองแล้วรอจนหมดเวลา (ลดเวลาเหลือ 1 นาทีตอนทดสอบ) -> อีกบัญชีจองแผงนั้นได้;
ระหว่าง hold อีกบัญชีจองไม่ได้; ส่งสลิปหลังหมดเวลาไม่ได้; สองบัญชีกดจองพร้อมกัน สำเร็จได้แค่ 1
```

```
ส่วน P0-4: หน้า "การจองของฉัน" สำหรับผู้เช่า

  เข้าได้เฉพาะผู้ใช้ที่ล็อกอินแบบไม่ใช่ anonymous
- query: bookings where tenantId == uid orderBy date desc ใช้ onSnapshot ให้สถานะอัปเดตทันที
  เพิ่ม composite index ใน firestore.indexes.json
  รวมประวัติจาก bookingHistory ของส่วน 3 ด้วย (ถ้ามี)
- แบ่งเป็นแท็บ: "กำลังจะถึง" (วันที่ >= วันนี้ตามเวลาไทย) และ "ที่ผ่านมา"
- แต่ละรายการแสดง: วันที่ (formatThaiDate), เลขแผง, โซน, ยอดเงิน, badge สถานะภาษาไทย
  (กำลังรอชำระ / รอตรวจสลิป / อนุมัติแล้ว / ถูกปฏิเสธ พร้อมเหตุผล / ยกเลิก / หมดเวลา)
  ใช้สีสถานะจาก utils/stallStatus.js ถ้ามี
- กดรายการแล้วเห็นรายละเอียด: ดูสลิปที่ส่ง (getDownloadURL จาก slipPath ตาม storage.rules),
  ข้อมูลร้านที่กรอกตอนจอง, เวลาที่จอง/อนุมัติ, ปุ่ม "ดูตำแหน่งบนผัง" ที่พาไปผังวันนั้นและไฮไลต์แผง
- ถ้าสถานะ 'hold' ที่ยังไม่หมดเวลา: ปุ่ม "ชำระเงินต่อ" กลับไปหน้าส่งสลิปพร้อมเวลานับถอยหลัง
- สถานะว่างเปล่า: ข้อความ "ยังไม่มีการจอง" และปุ่มไปหน้าผัง
- ในเมนูผู้ใช้ / navbar เพิ่มลิงก์ "การจองของฉัน" พร้อมตัวเลขการจองที่กำลังจะถึง
- ยังไม่ต้องทำการยกเลิกเองและการส่งสลิปใหม่ (อยู่ในงานรอบถัดไป)
- rules: ยืนยันว่าผู้ใช้อ่านได้เฉพาะ booking ของตัวเอง

ทดสอบ: จองหลายวัน -> เห็นครบเรียงถูก; admin อนุมัติ -> สถานะเปลี่ยนทันทีโดยไม่ต้อง refresh;
บัญชีอื่นไม่เห็นการจองของเรา; ดูสลิปได้; ใช้บนมือถือได้

## ส่วน 5: ค้นหาและกรองการจองในหน้า admin

```
ส่วน P0-5: หน้าจัดการการจองของ admin

- หน้าหรือแท็บ "การจองทั้งหมด" สำหรับ isAdmin() (แยกจากรายการรออนุมัติของระยะ 3 หรือรวมเป็นแท็บเดียวกัน)
- ตัวกรองฝั่ง Firestore query: ช่วงวันที่ (ค่าเริ่มต้น วันนี้ถึง +7 วัน), สถานะ (หลายค่าได้), โซน
  เพิ่ม composite index ที่จำเป็นใน firestore.indexes.json
- ช่องค้นหาข้อความ (ชื่อ ชื่อร้าน เบอร์โทร เลขแผง) กรองฝั่ง client จากผลที่โหลดมา
  และค้นเบอร์โทรโดยไม่สนขีดหรือช่องว่าง
- ตารางบนจอใหญ่ / การ์ดบนมือถือ: วันที่, แผง, โซน, ผู้เช่า, เบอร์ (กดโทรได้), ยอดเงิน, สถานะ
  เรียงตามวันที่และเลขแผงได้, แบ่งหน้าหรือโหลดเพิ่มทีละ 50 รายการ
- สรุปด้านบน: จำนวนแต่ละสถานะ และยอดเงินที่ approved ในช่วงที่กรอง
- กดรายการ -> รายละเอียดพร้อมสลิป และปุ่มที่มีอยู่แล้ว (อนุมัติ/ปฏิเสธ/ยกเลิก) ไม่ต้องสร้างใหม่
- มุมมอง "รายวัน": เลือกวันเดียวแล้วเห็นรายชื่อผู้เช่าทุกแผงเรียงตามเลขแผง ไว้ใช้หน้างาน
  มีปุ่มพิมพ์ (CSS @media print อย่างเดียว ยังไม่ต้องทำ PDF)
- เก็บค่าตัวกรองล่าสุดไว้ใน query string ของ URL (ถ้ามี router) หรือ sessionStorage

ทดสอบ: กรองวันที่ + สถานะได้ผลถูก; ค้นเบอร์ "0812345678" เจอแม้บันทึกเป็น "081-234-5678";
tenant เข้าหน้านี้ไม่ได้; พิมพ์มุมมองรายวันได้อ่านง่าย
```

## ส่วน 6: owner จัดการสิทธิ์ผู้ใช้

```
ส่วน P0-6: หน้าจัดการผู้ใช้สำหรับ owner

- หน้า "ผู้ใช้" เห็นเฉพาะ isOwner() (ซ่อนเมนูและกัน route ด้วย)
- รายการ users: ชื่อ, อีเมล, เบอร์, role, วันที่สมัคร, จำนวนการจอง (ถ้านับได้โดยไม่ query หนัก
  ถ้าหนักให้ข้าม) ค้นหาด้วยชื่อ/อีเมล และกรองตาม role แบ่งหน้าทีละ 50
- เปลี่ยน role ระหว่าง tenant <-> admin ด้วย dropdown + dialog ยืนยัน
  "ให้สิทธิ์ admin กับ [ชื่อ]? คนนี้จะแก้ผังและอนุมัติการจองได้"
- ห้ามแต่งตั้ง owner เพิ่มจาก UI และห้าม owner ลดสิทธิ์ตัวเอง
  (การเพิ่ม owner ให้ทำผ่าน Firebase Console เท่านั้น เขียนวิธีไว้ใน README)
- บันทึก roleUpdatedBy (uid) และ roleUpdatedAt (serverTimestamp) ทุกครั้งที่เปลี่ยน role
  และสร้างแจ้งเตือนถึงผู้ใช้คนนั้นว่าสิทธิ์เปลี่ยน
- rules: ตรวจว่าเปลี่ยน role ได้เฉพาะ isOwner(), role ใหม่ต้องเป็น 'tenant' หรือ 'admin',
  ห้ามเขียน role = 'owner', ห้ามแก้ doc ของตัวเองให้ role เปลี่ยน, ต้องเขียน roleUpdatedBy == request.auth.uid
  และแก้ได้เฉพาะฟิลด์ role, roleUpdatedBy, roleUpdatedAt (ใช้ diff().affectedKeys())
- ผู้ใช้ที่ถูกเปลี่ยน role ขณะออนไลน์: authStore ต้อง listen users/{uid} แล้วอัปเดต role ทันที
  ถ้าถูกลดจาก admin ขณะอยู่ Admin Builder ให้ออกไปหน้าลูกค้าพร้อมแจ้งเตือน

ทดสอบ: owner ตั้ง tenant เป็น admin -> คนนั้นเห็น Admin Builder ทันที; ลดกลับ -> หายทันที;
admin ธรรมดาเข้าหน้านี้ไม่ได้และแก้ role ผ่าน Firestore ตรงไม่ได้ (emulator test)
```

## ส่วน 7: ยอมรับกติกา และนโยบายความเป็นส่วนตัว (PDPA)

```
ส่วน P0-7: กติกาตลาด, เงื่อนไขการใช้งาน, นโยบายความเป็นส่วนตัว และการขอความยินยอม

หน้าเนื้อหา:
- สร้างหน้า (route ถ้ามี router ถ้าไม่มีให้เป็น modal ที่เปิดได้จากลิงก์) 3 หน้า:
  "กติกาตลาด", "เงื่อนไขการใช้งาน", "นโยบายความเป็นส่วนตัว" และลิงก์ที่ footer ทุกหน้า
- เนื้อหาเก็บเป็นไฟล์ markdown ใน src/content/ (หรือ public/) ให้ผมแก้ได้ง่ายโดยไม่ต้องแตะโค้ด
  ใส่เลขเวอร์ชันและวันที่มีผลไว้ต้นไฟล์ เช่น version: 2026-10-01
- กติกาตลาด: ให้ admin แก้ข้อความได้จากหน้า "ตั้งค่าตลาด" (เก็บใน markets doc พร้อม rulesVersion)
- เขียนโครงร่างนโยบายความเป็นส่วนตัวภาษาไทยจากข้อมูลที่แอปเก็บจริง (ตรวจจากโค้ด):
  เก็บข้อมูลอะไร (ชื่อ อีเมล เบอร์ ชื่อร้าน ประเภทสินค้า สลิปโอนเงิน ฯลฯ), เก็บเพื่ออะไร,
  ใครเข้าถึงได้, ใช้บริการภายนอกอะไร (Firebase/Google), เก็บนานแค่ไหน, สิทธิ์ของเจ้าของข้อมูล
  (ขอดู แก้ ลบ ถอนความยินยอม) และช่องทางติดต่อ
  ส่วนที่ต้องเป็นข้อมูลจริงให้ใส่ [กรอก: ...] ไว้ ห้ามแต่งชื่อบริษัท ที่อยู่ เบอร์ หรือระยะเวลาเก็บขึ้นเอง
  และใส่หมายเหตุต้นไฟล์ว่า "ร่าง ต้องตรวจทานก่อนเผยแพร่"

การขอความยินยอม:
- ฟอร์มสมัคร (รวมสมัครด้วย Google ครั้งแรก): checkbox บังคับ
  "ฉันยอมรับเงื่อนไขการใช้งานและนโยบายความเป็นส่วนตัว" พร้อมลิงก์
  บันทึก termsVersion, privacyVersion, consentAt (serverTimestamp) ใน users/{uid}
- ฟอร์มจอง: checkbox บังคับ "ฉันอ่านและยอมรับกติกาตลาด" บันทึก marketRulesVersion ใน booking
- ถ้าเวอร์ชันเงื่อนไขหรือนโยบายเปลี่ยน: ผู้ใช้เดิมเห็น modal ให้ยอมรับใหม่ก่อนจองครั้งถัดไป
- rules: การสร้าง booking ต้องมี marketRulesVersion; การสร้าง users doc ต้องมี consentAt

ทดสอบ: สมัครโดยไม่ติ๊ก -> สมัครไม่ได้; จองโดยไม่ติ๊ก -> ปุ่มยืนยันกดไม่ได้;
เปลี่ยนเลขเวอร์ชันในไฟล์ -> ผู้ใช้เดิมถูกขอให้ยอมรับใหม่; หน้าเนื้อหาเปิดได้โดยไม่ต้องล็อกอิน
```
