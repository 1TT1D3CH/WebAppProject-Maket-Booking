# Prompt: ปรับ UX/UI ให้ใช้ง่ายบน iPad และมือถือ

ใช้กับ repo "Dynamic Market Stall Booking System" (Vue 3 + Pinia + Vite + Tailwind + Firebase)

## ปัญหา

ตอนนี้เปิดบนมือถือหรือ iPad แล้วรู้สึกเหมือนเปิดเว็บคอมย่อส่วน: ปุ่มเล็กกดยาก, เมนูและแถบเครื่องมือเบียดกัน,
ต้องซูมทั้งหน้าเว็บเอง, modal ล้นจอ, ของที่ต้องเอาเมาส์ชี้ (hover) ใช้กับนิ้วไม่ได้

## ข้อควรรู้ก่อนใช้

- **โค้ดถูก reset กลับไป commit ก่อนวันที่ 2026-10-10** งานจาก prompt ที่ทำวันนี้หายไปแล้ว
  prompt นี้จึงสั่งให้ agent ดูโค้ดจริงก่อนเสมอ ไม่เดาว่ามี CanvasToolbar, BaseModal, router,
  หน้า "การจองของฉัน" ฯลฯ ถ้าไม่มี agent จะปรับเฉพาะหน้าที่มีอยู่จริง
- **อีกเธรดกำลังแก้บั๊กบันทึก/โหลดผังแผงอยู่** prompt นี้ห้ามแตะโครงข้อมูล Firestore, firestore.rules
  และโค้ดบันทึก/โหลดผังทุกจุด ถ้า agent เจอว่าต้องแก้ตรงนั้นจะหยุดถามก่อน
  แนะนำให้ทำ prompt นี้**หลัง**แก้บั๊กบันทึกผังเสร็จและ commit แล้ว จะได้ไม่ชนกัน
- agent จะ commit ให้ทีละส่วน แต่ **ไม่ push และไม่ deploy** จนกว่าคุณสั่ง

## วิธีใช้

1. เปิด coding agent ที่ root ของ repo วาง **"ส่วนหัว"** ตามด้วย prompt ของส่วนนั้น **ทีละส่วน ตามลำดับ**
2. ถ้ามีภาพหน้าจอจากมือถือ/iPad ที่ใช้ยาก แนบไปพร้อมส่วน 0 และเขียนในช่อง "จุดที่ผมใช้ยาก"
3. จบแต่ละส่วน ลองตามขั้นตอนทดสอบบนมือถือ/iPad จริง แล้วค่อยเริ่มส่วนถัดไป

| ส่วน | เรื่อง | หยุดถามก่อนไหม |
|---|---|---|
| 0 | สำรวจโค้ดและถ่ายภาพหน้าจอตั้งต้น 4 ขนาดจอ | **ใช่** (ส่งรายการปัญหา + แผนให้ดู) |
| 1 | พื้นฐานจอสัมผัส (viewport, ขนาดปุ่ม, ฟอนต์, safe area) | ไม่ |
| 2 | เมนูหลัก / header บนมือถือและ iPad | ไม่ |
| 3 | ดูผังด้วยนิ้ว (ลูกค้า): ซูม เลื่อน แตะแผง | ไม่ |
| 4 | modal และฟอร์มจอง บนจอเล็ก | ไม่ |
| 5 | หน้าแก้ผังของ admin บน iPad (และมือถือแบบเบา ๆ) | ไม่ |
| 6 | ตาราง/รายการ เป็นการ์ด + เก็บรายละเอียด + ทดสอบรวม | ไม่ |

ขนาดจอที่ใช้ตลอดทั้ง prompt:
- มือถือ 375×667 และ 390×844 (iPhone)
- iPad แนวตั้ง 768×1024 / 820×1180, iPad แนวนอน 1024×768 / 1180×820
- คอม 1366×768 และ 1440×900 (ต้องไม่แย่ลงกว่าเดิม)

## ส่วนหัว (ใช้ทุกส่วน)

```
คุณคือนักพัฒนา Vue 3 + Pinia + Vite + Tailwind CSS ที่ทำงานใน repo "Dynamic Market Stall Booking System"
(ระบบจองแผงตลาด มีผังตลาดที่ลูกค้าดูและจองแผง และหน้าแก้ผังแบบลากวางสำหรับ admin, เก็บข้อมูลใน Firebase)

เป้าหมายรวม: ทำให้ใช้งานบนมือถือและ iPad ได้ง่ายเหมือนแอปที่ออกแบบมาสำหรับนิ้ว
ไม่ใช่เว็บคอมที่ย่อส่วน โดยหน้าตาบนคอมต้องไม่แย่ลง

สำคัญ: โค้ดใน repo ถูก reset กลับไป commit ก่อนวันที่ 2026-10-10 ห้ามเชื่อชื่อไฟล์/ฟีเจอร์ที่ผมพูดถึง
จนกว่าจะเห็นในโค้ดจริง (เช่น CanvasToolbar.vue, BaseModal, vue-router, หน้า my-bookings อาจไม่มี)
ถ้าโค้ดจริงต่างจากที่ผมเขียน ให้ยึดโค้ดจริงและบอกในสรุป ถ้าโปรเจกต์ไม่ใช่ Vue ให้หยุดบอกผมก่อน

กติกา (ทุกส่วน):

2. ห้ามเปลี่ยนความหมายของข้อมูลในผัง: พิกัด x/y, w/h, การหมุน, หน่วย ต้องคำนวณเหมือนเดิมเป๊ะ
   การลากแผงด้วยนิ้วต้องได้ค่าเดียวกับการลากด้วยเมาส์ที่ตำแหน่งเดียวกัน
3. ห้ามตัดฟีเจอร์ทิ้ง ทุกอย่างที่ทำได้บนคอมต้องทำได้บน iPad ถ้าบนมือถือซ่อนไว้ ต้องเข้าถึงได้จากเมนู
4. ห้ามเพิ่ม dependency ใหม่ ถ้าจำเป็นจริง (เช่น library pinch-zoom) ให้ถามผมก่อนพร้อมเหตุผลและขนาด

5. ข้อความ UI ภาษาไทย ใช้สไตล์และ component เดิมของโปรเจกต์ รองรับ dark mode ทุกจุดที่แก้
6. ก่อนทุก commit รัน npm run build ต้องผ่าน และรัน lint / test:unit ถ้ามี script นั้น
   ถ้ารันไม่ได้ให้บอกตรง ๆ ห้ามบอกว่าผ่าน
7. commit ย่อยตามหัวข้อ ข้อความขึ้นต้น "feat(mobile): ..." หรือ "fix(mobile): ..."
8. ห้าม git push, ห้าม firebase deploy, ห้าม force push, ห้ามรันสคริปต์ที่แก้ข้อมูล Firestore จริง
   จนกว่าผมสั่งเองในแชท
9. ตรวจผลทุกส่วนที่ 4 ขนาดจอ: 375×667, 768×1024, 1024×768, 1440×900
   ถ้า repo มี Playwright หรือรันเบราว์เซอร์ headless ได้โดยไม่ต้องเพิ่ม dependency ให้ถ่ายภาพหน้าจอเก็บไว้ที่
   docs/mobile-ux/<ส่วน>-<ขนาด>.png (ไม่ commit ภาพถ้าเกิน 300 KB รวม) ถ้าทำไม่ได้ให้บอกว่าต้องตรวจเอง
10. จบแต่ละส่วน สรุป: ทำอะไร, ไฟล์ที่แก้, เรื่องที่ยังไม่ได้ทำ, และวิธีทดสอบบนมือถือ/iPad จริงทีละขั้น
```

## ส่วน 0: สำรวจและวางแผน (ยังไม่แก้โค้ด)

```
ส่วน 0: สำรวจหน้าจอทั้งหมดบนจอเล็ก แล้วเสนอแผน ยังไม่ต้องแก้โค้ด

จุดที่ผมใช้ยาก (ถ้าว่าง ให้หาเองทั้งหมด):
- ใช้บนมือถือแล้วรู้สึกเหมือนใช้เว็บคอมในมือถือ ใช้ยาก
- 

1. git log -5 --oneline และ git status ให้ผมดูว่าอยู่ commit ไหน มีไฟล์ค้างไหม
   (ถ้ามีไฟล์แก้ค้างที่ไม่ใช่ของงานนี้ ห้ามแตะ ห้าม stash/reset ให้บอกผม)
2. ทำแผนที่หน้าจอจากโค้ดจริง: แต่ละหน้า/view/modal ชื่อไฟล์อะไร ใครเห็นได้ (ทั่วไป / ลูกค้า / admin)
   สลับหน้าด้วยอะไร (vue-router, hash, v-if) และ component ผัง/แถบเครื่องมือ/inspector อยู่ไฟล์ไหน
3. ตรวจพื้นฐานและรายงานเป็นข้อ ๆ พร้อม ไฟล์:บรรทัด:
   - meta viewport ใน index.html
   - ใช้ h-screen / 100vh ตรงไหน (บน iOS แถบ Safari ทำให้ล้น)
   - breakpoint ที่ใช้ (sm/md/lg) และมีหน้าไหนออกแบบแค่จอใหญ่ (ความกว้าง fix เป็น px, sidebar ตายตัว)
   - ปุ่ม/ลิงก์ที่เล็กกว่า 44×44px บนจอสัมผัส
   - input ที่ font-size ต่ำกว่า 16px (iOS จะซูมทั้งหน้าเมื่อแตะ)
   - ของที่ใช้ได้เฉพาะ hover (tooltip, เมนูที่เปิดเมื่อชี้, ปุ่มที่โผล่เมื่อชี้)
   - การลาก/ซูมผัง ใช้ mouse events หรือ pointer/touch events, มี touch-action ไหม,
     ซูมด้วย wheel อย่างเดียวหรือเปล่า, pinch ได้ไหม
   - modal ที่สูง/กว้างเกินจอ, ปุ่มยืนยันหลุดล่างจอ, คีย์บอร์ดบังช่องกรอก
   - ตารางที่ต้องเลื่อนแนวนอน, overflow-x ทั้งหน้า
4. ถ้ารันได้ ให้เปิด npm run dev แล้วถ่ายภาพหน้าหลัก, ผังลูกค้า, modal จอง, หน้า admin แก้ผัง
   ที่ 375×667, 768×1024, 1024×768 (ภาพตั้งต้นไว้เทียบทีหลัง)
5. เสนอแผน:
   - ตารางปัญหา: หน้า | ปัญหา | ขนาดจอที่เจอ | ความรุนแรง (ใช้ไม่ได้ / ใช้ยาก / ไม่สวย) | จะแก้ในส่วนไหน
   - layout ที่จะใช้สำหรับแต่ละกลุ่มจอ (มือถือ / iPad แนวตั้ง / iPad แนวนอน + คอม) วาดเป็น ASCII ง่าย ๆ
     อย่างน้อยหน้าผังลูกค้าและหน้า admin แก้ผัง
   - รายการไฟล์ที่ต้องแก้ ยืนยันว่าไม่มีไฟล์ไหนอยู่ในกลุ่มห้ามแก้ตามกติกาข้อ 1
     ถ้ามี ให้บอกชัด ๆ ว่าเพราะอะไร
   แล้วหยุดรอผมตอบ
```

## ส่วน 1: พื้นฐานสำหรับจอสัมผัส

```
ส่วน 1: วางพื้นฐานที่ทุกหน้าใช้ร่วมกัน

1. index.html: <meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
   ห้ามใส่ user-scalable=no หรือ maximum-scale=1 (ผู้ใช้ต้องซูมหน้าเว็บได้เพื่อการเข้าถึง)
   แต่ส่วนผังให้จัดการ gesture เองด้วย touch-action ในส่วน 3
2. ความสูงจอ: เปลี่ยน h-screen / 100vh ของ layout หลักเป็น 100dvh (มี fallback 100vh)
   ใช้ class เช่น h-[100dvh] หรือ utility ใน CSS กลาง
3. safe area: header ชิดบน, แถบชิดล่าง, ปุ่มลอย ต้องเว้น env(safe-area-inset-*) (iPhone มีรอยบาก/home bar)
4. ขนาดเป้าแตะ: บนอุปกรณ์ที่นิ้วเป็นตัวชี้หลัก (@media (pointer: coarse)) ปุ่ม/ลิงก์/ช่อง checkbox
   ต้องแตะได้อย่างน้อย 44×44px (ขยายพื้นที่แตะด้วย padding ได้ ไม่ต้องขยายไอคอน) ระยะห่างระหว่างปุ่ม ≥ 8px
   ทำเป็น utility กลาง (เช่น class "tap" หรือ variant ใน tailwind.config) แล้วนำไปใช้
5. ฟอนต์: input, select, textarea ต้อง font-size ≥ 16px บนจอเล็ก (กัน iOS ซูมเอง)
   ข้อความเนื้อหาหลัก ≥ 14px บนมือถือ
6. hover: ของที่ต้อง hover ถึงจะเห็น ต้องมีทางเห็นด้วยการแตะ หรือแสดงตลอดบนจอสัมผัส
   ใช้ hover:… คู่กับ @media (hover: hover) หรือ variant ที่ Tailwind มี เพื่อไม่ให้สถานะ hover ค้างหลังแตะบน iOS
7. สร้าง composable useBreakpoint() (หรือใช้ของเดิมถ้ามี) คืน isPhone (<640), isTablet (640–1023),
   isDesktop (≥1024), isTouch (pointer: coarse) ด้วย matchMedia และ removeEventListener ตอน unmount
   ใช้เฉพาะตอนต้องสลับ component จริง ๆ เรื่อง layout ทั่วไปให้ใช้ class responsive ของ Tailwind
8. หน้าใดก็ตามต้องไม่มี scrollbar แนวนอนทั้งหน้าที่ 375px (เช็กด้วย document.documentElement.scrollWidth)

ทดสอบ: มือถือจริงหรือ DevTools 375px: ไม่มีเลื่อนแนวนอน, แตะช่องกรอกแล้วหน้าไม่ซูมเอง,
iPhone แนวนอนแล้วไม่มีอะไรถูกรอยบากบัง, คอม 1440px หน้าตาเหมือนเดิม
```

## ส่วน 2: เมนูหลักและ header

```
ส่วน 2: ทำ navigation ให้เหมาะกับจอเล็ก

1. มือถือ (<640px): header สูงไม่เกิน 56px เหลือ: ชื่อตลาด/โลโก้, ปุ่มแจ้งเตือน (ถ้ามี), ปุ่มเมนู
   ที่เหลือ (ลิงก์หน้า, สลับ dark mode, ข้อมูลผู้ใช้, ออกจากระบบ, เข้าหน้า admin) ย้ายเข้า drawer
   ที่เลื่อนออกจากด้านข้าง หรือ bottom sheet: ปิดได้ด้วยปุ่ม X, แตะพื้นหลัง, ปัดลง/ข้าง, ปุ่ม Back ของเครื่อง
   (ถ้าทำ Back ได้ง่ายกับการสลับหน้าที่มีอยู่ ถ้าซับซ้อนให้ข้ามและบอก)
2. ถ้าแอปมีหน้าหลักที่ลูกค้าใช้บ่อย 3–4 หน้า (เช่น ผังตลาด, การจองของฉัน, แจ้งเตือน, บัญชี)
   ให้ทำแถบนำทางด้านล่าง (bottom nav) บนมือถือ ไอคอน + ป้ายไทย แสดงหน้าปัจจุบันชัดเจน

3. iPad (640–1023px): header แถวเดียว ห้ามตัดบรรทัด ถ้าไม่พอให้ย้ายรายการรองเข้าเมนู "⋯"
4. แผงแจ้งเตือน (ถ้ามี): บนมือถือเปิดเป็นเต็มจอหรือ bottom sheet แทน dropdown เล็ก ๆ
5. header ห้ามบังผัง: ผังต้องคำนวณพื้นที่จาก "จอ - header - แถบล่าง" ไม่ใช่เต็มจอแล้วโดนทับ

ทดสอบ: 375px เปิด/ปิดเมนูได้ทุกวิธี, เข้าทุกหน้าที่เคยเข้าได้จาก header เดิม,
768px header ไม่ตัดบรรทัด, หมุน iPad ไปมาแล้ว layout ไม่ค้าง
```

## ส่วน 3: ดูผังด้วยนิ้ว (หน้าลูกค้า / คนทั่วไป)

```
ส่วน 3: ทำให้ดูผังและเลือกแผงด้วยนิ้วได้ลื่น (หน้าที่ลูกค้าและคนไม่ล็อกอินเห็น)
ห้ามแตะโค้ดที่โหลดผัง/แผงจาก Firestore ส่วนนี้แก้แค่การแสดงผลและ gesture

1. gesture บนพื้นที่ผัง ใช้ Pointer Events (pointerdown/move/up/cancel + setPointerCapture)
   และใส่ touch-action: none เฉพาะกล่องผัง (ส่วนอื่นของหน้ายังเลื่อน/ซูมปกติ):
   - ลากนิ้วเดียว = เลื่อนผัง
   - หนีบสองนิ้ว = ซูม รอบจุดกึ่งกลางระหว่างนิ้ว (จำกัด min/max zoom เดียวกับของเดิม)
   - แตะสองครั้ง = ซูมเข้า 2 เท่ารอบจุดที่แตะ (ถ้าซูมอยู่แล้วให้กลับพอดีจอ)
   - แตะครั้งเดียวบนแผง = เลือกแผง ต้องแยกจากการลากด้วยระยะขยับ ≥ 8px ถ้าขยับเกินถือว่าลาก ไม่ใช่แตะ
   - เมาส์บนคอม: ลาก, ctrl+scroll ซูมรอบเมาส์ ต้องทำงานเหมือนเดิม
   ถ้ามีโค้ด pan/zoom อยู่แล้ว ให้ปรับของเดิม ห้ามทำระบบซ้อนสองชุด
2. เปิดหน้ามาแล้ว "พอดีจอ" อัตโนมัติ (fit ทั้งตลาดในพื้นที่ที่เห็น) แทนการเปิดที่ 100% แล้วล้นจอ
   และ fit ใหม่เมื่อหมุนจอ (ถ้าผู้ใช้ยังไม่ได้ซูมเอง)
3. ปุ่มควบคุมลอยมุมล่างขวา (เหนือ safe area): [+] [−] [พอดีจอ] ขนาด 44px
   ซ่อนปุ่ม +/− บนจอสัมผัสได้ถ้ารก แต่ "พอดีจอ" ต้องมีเสมอ
4. แตะแผงแล้ว:
   - มือถือ: เปิด bottom sheet ครึ่งจอ แสดง เลขแผง, โซน, ขนาด, ราคา, สถานะ และปุ่ม "จองแผงนี้" ใหญ่เต็มความกว้าง
     ปัดลงหรือแตะนอก sheet เพื่อปิด, แผงที่เลือกมีกรอบเด่นและผังเลื่อนให้แผงไม่ถูก sheet บัง
   - iPad: แผงข้อมูลด้านข้าง (แนวนอน) หรือ bottom sheet (แนวตั้ง)
   - ข้อมูลที่เดิมโชว์ด้วย hover tooltip ต้องอยู่ใน sheet/แผงนี้แทน
5. ป้ายเลขแผงต้องอ่านออกเมื่อซูมพอดีจอบนมือถือ ถ้าแผงเล็กเกินจนตัวเลขเล็กกว่า ~10px ให้ซ่อนป้ายไว้
   แล้วแสดงเมื่อซูมเข้า (ไม่ใช่ย่อจนอ่านไม่ออก)
6. คำอธิบายสี (legend) และตัวเลือกวันที่/ตัวกรอง (ถ้ามี): บนมือถือย่อเป็นแถบเล็กด้านบนผัง แตะเพื่อขยาย
   ห้ามกินพื้นที่ผังเกิน ~15% ของความสูงจอ
7. ประสิทธิภาพ: ระหว่างลาก/หนีบ อัปเดตด้วย transform (translate/scale) ผ่าน requestAnimationFrame
   ห้าม re-render แผงทั้งหมดทุก pointermove

ทดสอบ (มือถือจริงดีที่สุด, DevTools ใช้ได้แค่ลากนิ้วเดียว):
เปิดผังแล้วเห็นทั้งตลาด, หนีบซูมแล้วจุดใต้นิ้วไม่กระโดด, ลากผังแล้วไม่เผลอเลือกแผง,
แตะแผงแล้ว sheet ขึ้นและกดจองได้, เลื่อนหน้าเว็บนอกผังได้ปกติ, คอมยังลาก/ซูมด้วยเมาส์ได้เหมือนเดิม
```

## ส่วน 4: modal และฟอร์มจอง

```
ส่วน 4: ทำ modal และฟอร์มให้ใช้บนจอเล็กได้

1. ถ้ามี BaseModal (หรือ modal กลาง) ให้เพิ่มรูปแบบตามขนาดจอ ถ้าไม่มี ให้ปรับ modal ที่มีอยู่ทีละตัว
   (ไม่ต้องสร้างระบบ modal ใหม่ทั้งหมดถ้าไม่จำเป็น บอกในสรุปว่าเลือกแบบไหน):
   - มือถือ: เต็มจอ (หรือ bottom sheet สำหรับ modal สั้น) header ติดบนมีชื่อ + ปุ่มปิด,
     ปุ่มหลัก (ยืนยัน/บันทึก) ติดล่างจอตลอด เหนือ safe area, เนื้อหาตรงกลางเลื่อนได้
   - iPad และคอม: กล่องกลางจอเหมือนเดิม แต่สูงไม่เกิน 90dvh และเนื้อหาเลื่อนได้ข้างใน
   - เปิด modal แล้วหน้าหลังเลื่อนไม่ได้ (lock scroll) และคืนค่าเมื่อปิด รวมถึงบน iOS Safari
2. ฟอร์มจองและฟอร์มอื่น ๆ (ล็อกอิน, สมัคร, โปรไฟล์):
   - เบอร์โทร type="tel" inputmode="tel", อีเมล type="email", ตัวเลข inputmode="numeric",
     autocomplete ให้ถูก (name, tel, email, current-password, new-password)
   - ป้ายชื่ออยู่เหนือช่อง (ไม่ใช่ข้างช่อง) บนมือถือ, ช่องกว้างเต็ม
   - ข้อความ error อยู่ใต้ช่องที่ผิด และเลื่อนไปช่องแรกที่ผิดเมื่อกดยืนยัน
   - คีย์บอร์ดเปิดแล้วช่องที่กำลังกรอกและปุ่มยืนยันต้องไม่ถูกบัง
     (ใช้ scrollIntoView({block:'center'}) ตอน focus และ visualViewport ถ้าจำเป็น)
   - ปุ่ม Enter บนคีย์บอร์ดไปช่องถัดไปหรือส่งฟอร์ม (enterkeyhint)
3. QR / รูปสลิป (ถ้ามี): QR ใหญ่พอสแกนจากอีกเครื่อง, มีปุ่ม "บันทึกรูป QR" ถ้ามีอยู่แล้วให้ใหญ่ขึ้น,
   ช่องแนบสลิปเปิดได้ทั้งกล้องและคลังรูปบนมือถือ (accept="image/*" ไม่ใส่ capture บังคับกล้อง)
   ห้ามแก้ logic อัปโหลด/บันทึกสลิป ปรับแค่หน้าตา
4. dialog ยืนยัน (ลบ, ยกเลิก): ปุ่มเรียงแนวตั้งเต็มความกว้างบนมือถือ ปุ่มอันตรายสีแดงอยู่ล่างสุด

ทดสอบ: 375px เปิด modal จองตั้งแต่ต้นจนกดยืนยันได้โดยไม่ต้องซูมหน้า,
ปุ่มยืนยันเห็นตลอด, แตะช่องเบอร์แล้วขึ้นแป้นตัวเลข, iPad แนวตั้ง/แนวนอน modal ไม่ล้น
```

## ส่วน 5: หน้าแก้ผังของ admin

```
ส่วน 5: ทำหน้าแก้ผัง (admin builder) ให้ใช้บน iPad ได้เต็มที่ และบนมือถือใช้งานเบา ๆ ได้
ห้ามแตะโค้ดบันทึก/โหลดผังเด็ดขาด ปุ่มบันทึกเรียกฟังก์ชันเดิมตามเดิม เปลี่ยนได้แค่ตำแหน่ง/หน้าตาปุ่ม

ก่อนเริ่ม: บอกผมว่าโค้ดจริงมี toolbar แยกไฟล์ไหม (CanvasToolbar.vue) มี inspector/แผงคุณสมบัติตรงไหน
และการลากแผงทำงานด้วย mouse หรือ pointer events

1. การลากแผง/วัตถุด้วยนิ้ว (ใช้ระบบ gesture เดียวกับส่วน 3):
   - แตะแผง = เลือก, ลากแผงที่เลือก = ย้ายแผง, ลากที่พื้นว่าง = เลื่อนผัง, หนีบ = ซูม
   - กันลากพลาด: เริ่มย้ายแผงเมื่อขยับเกิน 8px หลังแตะแผงที่ "เลือกอยู่แล้ว" เท่านั้น
     (แตะแผงที่ยังไม่เลือกแล้วลาก ให้เลื่อนผังแทน) บอกในสรุปถ้าเลือกวิธีอื่น
   - ระหว่างลาก แสดงตำแหน่ง/ขนาดเป็นเมตรเหนือนิ้ว ไม่ใต้นิ้ว
   - จุดจับปรับขนาด/หมุน (ถ้ามี) ต้องใหญ่ ≥ 24px ที่มองเห็น และพื้นที่แตะ ≥ 44px บนจอสัมผัส
   - snap และการคำนวณพิกัดใช้ฟังก์ชันเดิม ค่าที่ได้ต้องเหมือนการลากด้วยเมาส์
2. แถบเครื่องมือ:
   - iPad: แถวเดียว ไม่มี scroll แนวนอน ปุ่ม 44px รายการที่ไม่พอย้ายเข้าเมนู "⋯"
     ปุ่ม "+ เพิ่มแผง", "เพิ่มวัตถุ", "บันทึก" ต้องเห็นเสมอ
   - มือถือ: แถบติดขอบล่างจอ เหลือ [+ แผง] [วัตถุ] [บันทึก] [⋯] เมนูย่อยเปิดเป็น bottom sheet
   - ทุกปุ่มไอคอนมีป้ายไทยหรือ aria-label (บนจอสัมผัสไม่มี tooltip ให้ดู จึงควรมีป้ายสั้น ๆ ใต้ไอคอน)
3. inspector / แผงคุณสมบัติของแผงที่เลือก:
   - iPad แนวนอนและคอม: แผงด้านขวาเหมือนเดิม (หรือพับเก็บได้)
   - iPad แนวตั้งและมือถือ: bottom sheet ที่มี 2 ระดับ: ย่อ (แถบสรุป: เลขแผง + ปุ่ม แก้ไข / หมุน / ทำสำเนา / ลบ)
     และขยาย (ฟอร์มเต็ม) ผังยังเห็นและเลื่อนได้ตอน sheet ย่อ
   - ช่องตัวเลข (x, y, กว้าง, ยาว, ราคา) ใช้ inputmode="decimal" และมีปุ่ม −/+ ข้างช่องสำหรับปรับทีละขั้น
4. เมนูคลิกขวา (ถ้ามี) ต้องเปิดได้ด้วยการกดค้าง ~500ms บนจอสัมผัส (ยกเลิกถ้านิ้วขยับ) เป็นเมนู/sheet ใหญ่พอแตะ
5. คีย์ลัดที่มีอยู่ต้องยังทำงานบนคอมและ iPad ที่ต่อคีย์บอร์ด
6. มือถือ (<640px): แก้ผังได้ครบแต่จอเล็ก ให้แสดงแถบแจ้งครั้งเดียว (ปิดได้ จำใน localStorage ครอบ try/catch)
   "แก้ผังบนจอใหญ่หรือ iPad จะสะดวกกว่า" ห้ามบล็อกการใช้งาน
7. เตือนออกจากหน้าเมื่อยังไม่บันทึก (ถ้ามี beforeunload อยู่แล้ว) ให้ทำงานบน iPad ด้วยเท่าที่ Safari อนุญาต
   ถ้าต้องแก้ hasUnsavedChanges ใน store ให้หยุดถามก่อน (อยู่ในกลุ่มห้ามแก้)

ทดสอบบน iPad (หรือ DevTools 1024×768 และ 768×1024 โหมดสัมผัส):
เพิ่มแผง → ลากย้าย → ปรับขนาด → แก้ราคาใน inspector → บันทึก → รีเฟรชแล้วตำแหน่งตรงกับที่วาง,
ลากพื้นว่างแล้วผังเลื่อนโดยไม่มีแผงขยับ, คอม 1440px ทำงานเหมือนเดิมทุกปุ่ม
แจ้งผมด้วยว่าค่าพิกัดที่บันทึกจากการลากด้วยนิ้วเทียบกับเมาส์ ตรวจแล้วตรงกันอย่างไร
```

## ส่วน 6: รายการ/ตาราง และทดสอบรวม

```
ส่วน 6: เก็บหน้าที่เหลือและตรวจรวมทั้งแอป

1. ตารางทุกอัน (เช่น รายการการจอง, ผู้ใช้, โซน ถ้ามีในโค้ดจริง):
   - มือถือ: เปลี่ยนเป็นการ์ด แต่ละการ์ดมีข้อมูลสำคัญ 3–4 บรรทัด + ปุ่มการกระทำขนาด 44px
     เบอร์โทรเป็นลิงก์ tel: กดโทรได้
   - iPad: ตารางเดิมได้ถ้าไม่ล้น ถ้าล้นให้ซ่อนคอลัมน์รอง (ไปอยู่ในหน้ารายละเอียด)
   - ตัวกรอง/ค้นหา: บนมือถือรวมเป็นปุ่ม "ตัวกรอง (2)" เปิด bottom sheet
2. สถานะว่าง / กำลังโหลด / error: ข้อความไทยกลางจอ อ่านง่ายบนจอเล็ก ไม่ใช่ตัวเล็ก ๆ มุมจอ
3. toast / แจ้งเตือนชั่วคราว: บนมือถืออยู่ด้านบนหรือเหนือแถบล่าง ไม่บังปุ่มหลัก
4. dark mode: ไล่ทุกหน้าที่แก้ในส่วน 1–6 ที่ 375px ว่าไม่มีตัวอักษรกลืนพื้น
5. accessibility เบื้องต้น: ใช้คีย์บอร์ดอย่างเดียวบนคอมได้ครบเหมือนเดิม, ทุก sheet/drawer มี role="dialog"
   และคืน focus เมื่อปิด, ซูมหน้าเว็บ 200% แล้วไม่มีอะไรหาย
6. ตรวจรวม: ไล่ทุกหน้าที่ 375×667, 390×844, 768×1024, 1024×768, 1440×900 ถ่ายภาพเทียบกับส่วน 0 (ถ้าทำได้)
   และรายงานตาราง: หน้า | ขนาดจอ | ผ่าน/ไม่ผ่าน | หมายเหตุ
7. ยืนยันด้วย git diff --stat ตั้งแต่ commit ก่อนส่วน 1 ว่าไม่มีการแก้ firestore.rules, firebase.json,
   และไม่มีการแก้ฟังก์ชันบันทึก/โหลดผังหรือ onSnapshot (ถ้ามี ให้ชี้ว่าเป็นบรรทัดไหนและเพราะอะไร)

สรุปสุดท้ายให้ผม:
- ก่อน/หลัง ของแต่ละหน้าบนมือถือและ iPad (สั้น ๆ หน้าละบรรทัด)
- รายการ commit ทั้งหมดของงานนี้
- ขั้นตอนทดสอบบนโทรศัพท์และ iPad จริง ผ่าน npm run dev -- --host (เปิดจาก IP เครื่องในวง Wi-Fi เดียวกัน)
- สิ่งที่ยังไม่ได้ทำ และสิ่งที่ต้องรอให้งานแก้บันทึกผังเสร็จก่อน
- คำสั่ง push / deploy ที่ผมต้องรันเอง (ยังไม่ต้องรัน)
```
